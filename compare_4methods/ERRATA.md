## E-01 · DA3 高斯与相机位姿差 1.81 倍尺度（2026-11-06 发现 / 修复）

### 症状

`ppt_assets/fig10_p1_renders.png` 第 2 列「DA3 直出」：视角 0 尚可（略偏白偏软），
视角 16 **整幅融化、人物完全消失**。第一反应怀疑位姿有偏差，**不是**。

### 根因

`Depth-Anything-3/src/depth_anything_3/model/da3.py:400-415` `_apply_depth_alignment()`：

```python
scale_factor = least_squares_scale_scalar(valid_metric_depth, valid_depth)
output.depth      *= scale_factor
output.extrinsics[:, :, :3, 3] *= scale_factor
output.is_metric = 1
output.scale_factor = scale_factor.item()
# ← gaussians.means / gaussians.scales 没有乘
```

即：**depth 与相机被拉到米制，高斯留在对齐前的坐标系**。我们的 `97/98` 把
"官方导出的 PLY（raw 尺度）"与"`cameras.npz`（米制）"混用，于是点云整体只有真实
尺寸的 **1/1.81 ≈ 0.55**。

DA3 自己是知道的——`utils/export/gs.py:91-93` 渲视频时反过来把相机缩回去：

```python
if prediction.is_metric and scale_factor is not None:
    tgt_extrs[:, :, :3, 3] /= scale_factor
```

### 为什么"只有参考视角看着正常"

参考相机在世界原点，缩放是**以原点为中心的径向缩放**。对针孔相机 `u = fx·x/z`，
点沿自身视线滑动不改变投影 → 帧 0 画面几乎不变。其余视角看到的是横向位移，
量级 ≈ `(1−1/1.81)·d ≈ 0.45·d`：2 m 处约 0.9 m，接近半个画面。

### 证据（`99_diag_gs_ply_perview.py` / `99b_diag_umeyama.py`）

| 视角 | 到帧 0 距离 | 高斯回投自身相机误差 | ‖means − 深度抬起点‖ |
|---|---|---|---|
| 0 | 0.00 m | **1.19 px** | 0.85 m |
| 1 | 0.18 | 37 px | 0.83 |
| 4 | 0.81 | 151 px | 0.88 |
| 16 | 1.38 | 200 px | 0.98 |
| 8 | 1.78 | 193 px | 0.91 |

- 纯缩放拟合（只允许 s，不允许 R/t）：**s = 0.552 → 隐含 scale_factor 1.81**，
  逐视角 0.50~0.52 高度一致；
- 3D 距离 **恒定 ~0.9 m**、而像素误差 1→200 px 跨越两个量级 —— 只有"以帧 0 为原点的
  径向缩放"能同时解释这两个数。

### 影响范围（哪些结论要改）

| 对象 | 影响 |
|---|---|
| P0 三项（分辨率 / SH / 视角数） | **全部在错误口径下测**，需重测 |
| P0 结论「质量随到参考视角距离单调衰减，瓶颈是跨视角几何不一致」 | **降级为待重测**：该曲线很可能主要是口径错位，不是模型能力 |
| P1 前馈 init 两组（20.14 / 21.72 dB） | 是在错位 0.9 m 的条件下硬撑出来的，需重测 |
| P1 结论「多壳拓扑是重影主因」 | **降级**：主因是口径，多壳（厘米级）是残余 |
| fig6（DA3 原生高斯头）、fig10 第 2 列 | **图不可用**，必须重出 |
| P1 的「COLMAP init」两组（22.23 / 24.33 dB） | **不受影响**：点云由 depth 反投影而来，与位姿同源同尺度 |

### 修复

- 新增 `da3_frame.py`：`gaussians_to_metric(pred)` —— 导出前把 `means/scales` 乘 `scale_factor`；
- `98_da3_ff_init.py` / `97_da3_gs_export_full_sh.py`：导出前调用，并把
  `scale_factor` / `gs_scale_applied` 写进 `cameras.npz` 与 summary；
- `98b_ply_to_3dgs_ckpt.py`：读 npz 断言 `gs_scale_applied == 1`，否则直接退出
  （宁可报错，不要静默生成错尺度的 ckpt）；
- `94_render_da3_gs.py`：无需改（PLY 为米制后与 npz 自洽）。

### 重测计划

1. 修复后「DA3 直出」32 视角重渲 + PSNR（本次先做，用于出对比图）；
2. P0 三项按新口径重测（**旧数字全部作废**）；
3. P1 前馈 init 两组按新口径重跑（预期重影大幅减轻）。

20.14"，差距只剩 1.2 dB，**前馈初值的价值被高估/低估的判断全部作废，需重跑**。

### 重测结果（2026-11-07 00:54，P1 三组已闭环）

按 `P1_EXPERIMENTS.md` §5 预注册的判据重跑（同场景、同超参、同 32 视角，唯一差别是初值 PLY
是否乘 1.9988）：

| 组 | 旧 PSNR | **新 PSNR** | Δ | 新 SSIM | 新锐度 | 训练 |
|---|---|---|---|---|---|---|
| 前馈 415 万 + 2k | 19.67 | **25.21** | **+5.54** | 0.859 | 822 | 236 s |
| 前馈 415 万 + 5k | 20.14 | **25.51** | **+5.37** | 0.856 | 901 | 519 s |
| 前馈 57 万 + 5k | 21.72 | **25.17** | **+3.45** | 0.858 | 845 | 205 s |

**三条预注册判据全部命中「推翻」分支**：

1. A1（25.51）比稀疏点云 + 5k（22.23）高 **3.28 dB** → 旧结论「加速来自少跑步数而非前馈初值」
   **不成立**；正确说法是"前馈初值 + 少跑步数"。
2. A1（25.51）> A2（25.17）→「点数越多越差」**不成立**，稠密略优。
3. A1−A2 从 1.58 dB 缩到 0.34 dB →「opacity 分布不匹配导致叠糊」**降级为主因之一而非主因**。

**视觉侧的第二个独立验证**（`fig12_e01_retest_renders.png`）：旧口径的
「前馈 + 5k」在视角 0 人物外面套一层半透明壳、视角 16 人物错位；
米制版重影完全消失。**"重影 = 0.9 m 错位下优化器长出第二套壳"这一归因成立。**

**corr(到参考视角距离, PSNR) 也翻正为 0**（旧 +0.50 → 新 +0.07）：
训练之后，"离参考视角多远"不再是质量因子。P0 的 −0.62（未训练直出）仍存在，但很弱。

**代价**：A1 的 519 s 有 4.2 倍于 A2 的 205 s，换来 +0.34 dB；
甜点因此落在 **415 万 + 2k 步 = 236 s / 25.21 dB**（端到端 4.5 min）。

⚠️ **仍未闭环的部分**：P0 三项里 **SH rest 已于 2026-11-07 02:35 按米制口径重测闭环**，
判定 **B（无效）**：Δ = +0.23 dB（初始 degree=2 时 +0.26，两套时间表几乎相同），
且差值图显示差异全在背景木纹/书架，人脸区 ±0.00~0.09 dB —— 详见
`P0_EXPERIMENTS.md` §R-2。分辨率与视角数两项仍未重测，优先级已被下调
（见 `P1_EXPERIMENTS.md` §5.4）；但重测中顺带发现**训练分辨率 `RES=2`（720×960）
与评测归一化 378×504** 这个一直存在的口径，人脸在评测分辨率下仅 ~40 px，
它比"外观容量"更能解释"背景清楚、人脸糊"——见 §R-2.5。

### E. 归因纪律（2026-11-07 全链路审计新增）

- [ ] **E1 以 PLY / npz 为"真值"之前，先做内存 ↔ 文件对账**：
      `audit_6_ply_roundtrip.py` 逐属性比（means/scales/opacity/rot/f_dc），
      判据 = 相对误差 < 1e-5。否则导出端一旦错位，下游所有检查会**自洽地错**。
- [ ] **E2 判"参数口径"不能看 PSNR，要看增益扫掠的峰位**：
      整体乘一个 k（opacity / scale）扫 1~16，峰在 k≈1 = 口径正确；
      峰在 k≫1 才是成倍错（logit↔线性、σ↔3σ、漏乘 scale_factor）。
      PSNR 本身的 ±1 dB 抖动会被误读成口径问题。
- [ ] **E3 像素当量一律用"渲染时的焦距"折算**：
      `σ_px = σ_m / z × fx_render`，其中 `fx_render = fx_process × (原图宽/处理宽) / RES`。
      写成 `fx × RES` 会差 3.8 倍（本次 audit_7 第一版就是这么错的，结论方向没变但数字全错）。
- [ ] **E4 说"糊/重影"必须能拆到项**：用 `audit_2_render_decomp.py` 的三组
      （all / self / other）在同一像素集上比。但 **`÷α` 那一组不能当几何误差读**（见 E5）。
      只看 all 无法区分"单视角几何错"与"跨视角叠加糊"。
- [ ] **E5 `÷α` 只在 α 接近 1 时可用**：本次单层 α 中位 0.036，unpremultiply 把噪声放大
      ~14 倍，`19.69 dB` 于是被噪声主导，据此说"单视角几何偏 4.2 dB"是错的
      （真实残差 ~1 px 横向 + 26~42 mm 沿视线，由 `audit_8` 直接量得）。
      要判几何就投回像素量残差，不要拿 PSNR 反推。
- [ ] **E6 报"DA3 直出"必须是官方口径，不是 PLY 口径**：官方渲染用**内存里的全 SH + 全部
      610 万点**；我们的 PLY 是 `prune 0.9 + border + dc_only`，只有 484 万点、79.4% 像素。
      同一份前向：**22.11 dB（官方）vs 18.97 dB（PLY）**，差 3.14 dB 全在导出选项
      （全 SH +1.15、不裁剪 +2.34）。两者不可混用于跨方法对比。
- [ ] **E7 换表示/换光栅器前，先验"哪个轴是厚度轴"**：DA3 的 σ 是三轴独立 sigmoid、
      **没有排序**，实测最小轴 **99.69% 落在 index 0**（610 万点全量）。而 2DGS 的 CUDA 只读
      `scales[0], scales[1]`、第三维硬编码 1.0（`Projection2DGSFused.cu:152`）。
      直接喂 → `s0≈0` 被当成切平面内的一轴 → 零宽刀片，屏幕上几乎消失。
      必须先查 `argmin(σ)` 的索引，再重排 `s'=[s1,s2,s0]` 并同步置换旋转矩阵的列。
      **2026-11-08 已量化（`audit_15` 的 naive 档）**：不重排直接喂 2DGS，view 0/8/16
      逐视角 **−5.52 / −4.21 / −5.70 dB（均值 −5.14）**。不是"看起来消失"，
      是"还在渲染但整体掉 5 dB"——**更难靠肉眼发现**，所以这条必须是闸门而不是提醒。
      同理：任何"假设某轴有特定含义"的转换，都要在转换前后各量一次不变量。
- [ ] **E8 读 3DGS PLY 的 SH rest 是 channel-major**：DA3 写盘用
      `harmonics[...,1:].flatten(start_dim=1)`，即 `[ch0 的 K 个, ch1 的 K 个, ch2 的 K 个]`；
      gsplat 要的是 `(N, K, 3)`。必须 `reshape(N,3,K).transpose(0,2,1)`。
      排错的结果**不会崩、也不会明显变色**（DC 项照旧），只表现为"颜色对但方向感怪"，
      极难靠肉眼发现。兜底手段就是 E6 那条对照：**PLY 全 SH 渲染必须等于内存全 SH 渲染**
      （本次 22.11 vs 22.11，差 0.005 dB），不等就是排列错了。
- [ ] **E9 读 PLY 头不要假设 4096 字节**：DA3 的 header 因字段数变化（DC 17 字段 / 全 SH 41 字段）
      长度不同，必须读到 `end_header` 行尾拿真实偏移。audit_8 第一版用了 4096，
      属性全体错位，view 16 自投影残差算出 614 px，差点当大 bug 报上去。
- [ ] **E10 gsplat 1.5.3 的 `rasterization_2dgs` 有两个硬限制**（2026-11-08 `audit_15a` 实测）：
      ① **没有 `normals` 参数** —— 盘法向在光栅器内部由 `quats` 推出的旋转矩阵**第三列**决定，
         既传不进去也改不了。想控制法向，唯一入口是"把哪个轴排到第三列"。
      ② **`sh_degree=None` 时不可用** —— `rendering.py:1503-1520` 那段 "Compute the per-view
         colors" 被整块注释掉，colors 停在 `(N,3)`，下游断言 `colors.shape[:-2] == (B,C,N)`
         直接失败。只能传 SH 系数 `(N,K,3)` + `sh_degree`。
      另：`render_mode="RGB"` 时 `normals_from_depth / distort / median_depth` 全是 `None`，
      要拿它们必须 `RGB+ED` 或 `RGB+D`。
- [ ] **E11 单视角预测的一致性 ≠ 融合结果的下界**（2026-11-08 I-03 推翻的假设）：
      曾把「DA3 输入深度在掠射区的 0.80% 跨视角一致性」当成渲染深度的下界，
      据此判 I-03 必负。实测 2DGS 的 median 深度拿到 **0.41%**，比"下界"还好一倍。
      原因：输入深度是**单视角独立预测**，0.80% 里含单视角噪声；渲染深度是
      **610 万高斯多视角融合**的结果，median 取最近可见壳，天然把它平滑了。
      → 要定"下界"，得用**融合后的表面**量，不能用单视角预测。否则会系统性低估改进空间。
- [ ] **E12 人脸窗必须逐视角标定，不能用一张固定框**（2026-11-09 I-03b 撞出来的口径事故）：
      `audit_14` 起沿用 `FACE=(0.35,0.105,0.565,0.335)`（归一化）。人物在 32 视角里水平位置差很多：
      view 0 人头 x **168~212**、view 8 x **218~268**、view 16 x **178~235**。
      固定框（x 132~213）在 view 8 落在**书架**上——书架是高频平面，Laplacian 方差远大于人脸，
      于是"人脸锐度"整体被抬高 **+142 ~ +180**，"人脸 PSNR"也偏了 −0.19~−2.57。
      → 一个画面上有多个高频区域的场景里，**框错位置的代价与换方案等价**。
      定框办法：渲染图 + 像素刻度网格（`audit_21b_face_box_grid.py`）逐视角标定，标完必须**看一眼裁出来的图**。
      教训：任何"区域指标"在第一次报数之前，先存一张裁切图自己看。
- [ ] **E13 gsplat 1.5.3 的 `rasterization_2dgs` 忽略 `eps2d`**（2026-11-09 `audit_20_eps_sweep` 实测）：
      `eps2d ∈ {0.3, 0.1, 0.01}` 三档，PSNR/人脸/锐度**逐位相同**（21.69 / 19.42 / 343 / 443）。

- [ ] **E14 "把参数给正确答案"不一定更好 —— oracle 是换表示前的必做闸门**（2026-11-09 I-03b）：
      给 2DGS 喂 GT 深度图法向（覆盖率 65.1%），全图 PSNR **−0.71**、人脸 **−1.16**，

      → 由此可知：I-03 的损失**不能归因于法向**。若当初直接去重训法向正则（I-04），
      会花几十倍成本得到同一个负结果。
      配套订正：`audit_12` 的"56.9~66.4°"是逐视角/来源像素/含裁剪掩膜口径；I-03b 在 oracle 点上
      直接量到 **48.3°（p10 17.4°，仅 3.6% 落在 10° 内）**。两者都说明"没学对"，但**不是同一个量**。
- [ ] **E15 转视角展示前先量「相机方位角覆盖」**（2026-11-09 环视视频撞出来的）：
      这批 32 视角只覆盖 **252.7°**，−147° → −40° 之间 **107° 没有任何观测**，

      画面出现横向条纹/拖影 —— 极易被当成"重建器坏了"。
      先跑 `audit_23_coverage.sh` 看最大缺口；>30° 就别做 360° 展示，或明确标注缺口区间。
      同理，`look_at` 这类相机构造要三道自证（视向符号 / 注视点 / 手性），
      任一写反都会得到"人在背后"或"整幅转 180°"的画面，而参数看起来完全正常。
- [ ] **E16 3DGS `cameras.json` 的 `rotation` 存的是 c2w，不是 w2c**（2026-11-09 五方法视频）：
      按 3DGS 源码习惯把 `rotation` 当 world→camera（forward = 第 3 行）来算视线，
      与 DA3-GS 基准的夹角中位 **97.6~106.2°**（近乎正交，一眼是"错得离谱"而不是"有点偏"）。
      改成 forward = **第 3 列**（c2w）后 **0.11~0.25°**。
      → 判据要写成"四种解读（行± / 列±）全试，取视线夹角最小者"，别凭源码印象。
      四种都试的成本是几行代码，猜错一次的成本是整个视频白渲。
- [ ] **E17 跨方法对比必须先做"尺度对齐"，否则同一轨迹根本无从谈起**（2026-11-09）：
      DA3-GS 是 metric（`is_metric=1`、`scale_factor≈2.0`），另外三个前馈方法活在 VGGT 系，
      Umeyama 出来的 s = **2.25 ~ 2.28**（差 2.27 倍）。不做这一步，五方法各渲各的，
      半径/仰角/物体大小全不同，"相机轨迹相同"只是五个视频恰好都绕了一圈。
      对齐后残差 0.27~1.03% 半径、视线 0.11~0.46° —— 这个残差量级本身就是"对齐可信"的证据。
- [ ] **E18 「正方形输出」多半是画布问题，不是几何压扁**（2026-11-09 QuerySplat）：
      QS 的 K 是 fx≈fy≈494、cx=cy=256（512² 画布）→ 方形像素 + 方形视场，
      垂直只到 **54.8°**，而 GT 是 **68.6°**。原先以为"非等比 resize 把画面压扁了"，
      于是横向压 0.75（B 方案）—— PSNR 只从 11.95 动到 11.96，**几乎没有变化**，
      说明压扁假设是错的（真压扁的话对齐后应该显著变好）。
      正确解 D：**焦距等比缩 0.75 放进 3:4 画布**（像素仍方形），垂直视场自然张到 69.2°，
      PSNR **16.55**（+4.6 dB）。
      → 教训：遇到"画幅不一致"，先分清是**像素非方形**（要压）还是**视场比不同**（要等比缩焦距）。
      判据是"改完 PSNR 动没动"，动不到 2 dB 就是方向错了，别接着调参数。

## E-02 · 高斯 scale 的数字口径不一致（2026-11-06 订正）

P1 台账里写的「DA3 的 scale 中位数 0.8 mm」是**早期一次性统计**，与最终 PLY 不符。
按 `gs_ply/0000.ply` 实测（4,838,397 点）：

| 轴 | p1 | 中位 | p99 |
|---|---|---|---|
| 0 | 3.2e-9 m | **8.5e-9 m** | 5.0e-3 |
| 1 | 8.2e-5 m | **1.46e-3 m** | 4.7e-2 |
| 2 | 1.0e-4 m | **3.72e-3 m** | 3.3e-2 |

即高斯不是"小椭球"，而是**近乎零厚度的薄盘**（1.5 mm × 3.7 mm × ~1e-8 m），
在自身视角折合 0.3 / 0.8 像素。结论方向不变（远小于像素 → alpha 欠饱和 → 偏白），
但"小椭球"这个描述要换成"薄盘"，且它同时解释了**掠射视角下薄盘退化成线、alpha 归零**
（远端视角"看不到人"的第二重原因）。

opacity 中位 0.036（25% 分位 0.013、90% 分位 0.107）这条是准确的，保留。

**2026-11-07 补充**：上表是 raw 尺度（未乘 1.9988）的 PLY。米制 PLY `佳佳抱枕_p1m/gs_ply/0000.ply`
实测为 **1.7e-8 × 2.9e-3 × 7.4e-3 m**（正好 2 倍），opacity 分布完全不变（中位仍 0.0356）。
"薄盘"的判定与像素足迹（自身视角 0.3 / 0.8 px）**不因折算而改变**——因为相机同步放大 2 倍，
屏幕足迹是尺度不变的。P0/P1 里"薄盘导致 alpha 欠饱和 → 偏白"这条继续成立。
