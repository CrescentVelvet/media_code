## E-14：两个 3DGS"评测未通过"是渲染约定，不是模型（10:45）

- **根因两个，都在渲染约定上**：
  ① **底色**。`cfg_args` 里 `white_background=False`，模型学的是黑底合成；我硬编码白底。
     本场景高斯 alpha 中位只有 0.979，2% 半透明边 × 255 ≈ 5 灰阶系统偏移 → 自洽 14.9 vs 37.4。
     **不是这两个方法的问题**：六方法双盲探针**全部**偏好黑底（DA3-GS +4.14、VGGT-Ω +7.51、
     DA3+3DGS +7.10、v2 +1.11、SA +0.43、QS +0.04）→ 历史 E-12/E-13 全部白底是全局偏差。
  ② **主点**。官方 3DGS 只从 FOV 造投影，主点隐含在画布中心，`cameras.json` 没有 cx/cy。
     用 COLMAP 真值 cy=952.9 渲它的 PLY = 18.83 dB，用画布中心 479.5 = **42.93 dB**（差 24 dB）。
     修法：`own_intrinsics()`，json 相机一律 cx=W/2、cy=H/2。`CROP_SQ` 的裁窗本来以主点为中心，
     所以 holdout（GT 相机）天然满足，只影响自洽口径 `self3_ownK`。
- **剩下 25 dB 是像素网格，不是画质**：原生 720×960 只在裁窗内算 **43.37 dB**；全幅渲完再缩
  718→720 = 22.6；直接渲方形 720²（平移最优 dy+4/dx+1）= 27.3；512² 评测口径 17.9。
  758k 高斯 / 3 视图 = 把训练像素网格背下来了，任何重采样掉 20 dB。**跨分辨率评测对
  3 视图过拟合 3DGS 有系统性惩罚**，必须配区域指标，不能和"画得糊"混。
- **区域指标**（`compare_4methods/region_metrics.py`）：mask 内 Laplacian 方差比、高频能量比、
  边缘 chamfer F1(2px)、鬼影率(渲染边缘距 GT 边缘 >4px)、GT→渲染光流中位位移与散度。
  mask 用 SAM3 person/face/hand；**必须按 person 主体门控**（单帧曾检出 5 个背景海报人脸）。
  自证：GT 加 σ=1.6 模糊 PSNR 仍有 29 dB、锐度比已掉到 0.05；叠加 6px 位移重影 → 鬼影率 0.10；
  横向放大 8%（脸变宽）→ 散度 +0.40、鬼影率 0.43。
- **结论与用户判断一致且更强**：PSNR 第 1 的 QuerySplat 锐度第 6（人脸高频只剩 3%，
  独立复核 Laplacian 方差比 0.047）；PSNR 第 4 的 DA3+3DGS 锐度第 1。六方法 PSNR 只差 4.0 dB、

## H100 保活与监控（`h100/10_*`、`11_gpu_monitor.py`）
- **占空比的真元凶是 CPU 喂不饱 GPU**：`--intensity mid` 标称 75%，实测仅 **17%**、功耗 128W。
  根因不是睡眠折算公式，而是 **Python 每秒只能提交约 490 次 matmul**（4096 方阵 bf16 单次
  GPU 侧约 0.29ms，GPU 需约 2900 次/s 才喂满），GPU 每秒只拿到约 0.17s 的活就断了。
  **解法 CUDA Graph**：把 64 次 matmul 录成一张图，`replay()` 一次 CPU 调用 → GPU 背靠背，
  单图 18ms。实测 mid 17%→**76%**、low→37%（标称 35%）。录制失败自动退回逐次提交。
  教训：调占空比之前先量「单次 kernel 的 GPU 耗时 × CPU 提交速率」，否则算法再对也白搭。
- **`nvidia-smi utilization.gpu` 是"上次查询到现在"窗口内活跃占比**，采样点落在睡眠段恒读 0%
  → 采样必须放在 burst 刚提交完、`synchronize` 之前。日志里另给「实测占空比」（CUDA event
  累加真值）用于核对，两者会不一致是正常的（low/mid 的 util 列会在 0/100 间跳）。
- **8 卡 spawn 必须逐子进程收窄 CVD**：继承父进程 `CUDA_VISIBLE_DEVICES="0,1,..."` 时各子进程
  都用 `cuda:0`，全挤在卡 0。要在 `import torch` **之前**设成单卡号 + `device_count()==1` 自检。
- **环境变量必须 `HOLD_` 前缀**：裸 `SIZE` 被 conda binutils 激活钩子覆盖成
  `x86_64-conda-linux-gnu-size`（argparse 直接报 invalid int）。
- 实测：8 卡 high = util 99~100% / 347W 每卡 / 20.8 GiB（垫 20G）；low ≈ 均 210W/卡。
  CLI `./10_hold.sh start [gpus] [hours] [intensity] [memgib]` / `ls` / `stat` / `stop` / `tail`；
  监控 `python3 11_gpu_monitor.py [--interval N] [--once] [--jobid ID] [--probe]`。

### 保活日志"读数造假"复盘（同日二轮，比上面那条坑更深）

  全部 8 行，`out[0]` 恒为物理卡 0。原实现"worker 里 CVD 已收窄，不带 -i 只列一张"是错的
  → 8 个 worker 全读卡 0。**`-i <数字>` 才精确**（`-i GPU-<uuid>` 会报 No devices found，
  torch uuid 不带 `GPU-` 前缀）。索引映射用 `torch.cuda.get_device_properties(0).uuid` 对齐验证无漂移。

  （19~48 ms）长约 20×。在主循环同步采样 = 每轮 1 秒不提交 kernel，GPU 队列被跑空，
  采样窗全落在空档 → 8 卡日志恒读 `0%/102W/58C`，而外部同时刻 `100%/349W/66C`。

- **FREE_MEM 口径**（用户问「8 卡都占了为什么还有大量空闲内存」）：`sinfo %e` = 节点内核

## canada_h100 监控彻底解耦（第八轮）

- 峰哥的核心诉求原话：「我开了个监控脚本，时刻监控，这期间我可以停止任务，可以挂保活
  脚本，也可以开始训练，这么多脚本都不应该影响监控脚本的状态」。→ **监控是与作业无关的
  常驻进程，作业的增删改全不影响它，只有 Ctrl-C 能结束。**
- **真实病根不是"两个脚本是同一个"**（本来就是独立文件），而是**数据通道耦合**：登录节点
  无 NVML，监控必须 `srun --jobid=<某作业> --overlap` 借计算节点采样。作业一 `scancel`，
  采样器 srun 步骤被 `CANCELLED`，旧代码收到 `eof` 就 `return` → 表现成"监控跟着停了"。
  另：`cmd_stop()` 里从来只有 `scancel`，**没有任何 pkill/killall**，可排除"stop 杀了监控"。
- **主循环重写四段式**：① 每 `--rescan` 秒扫 `squeue`，只决定跟谁；② 只对 `want_jid`
  （**已确认 RUNNING**）起会话，绝不拿死 ID 撞 srun；③ 收帧，`eof`/`fatal` 只收会话 +
  退避重试、不退出；④ 渲染，等待态 `sleep(max(0.5, rescan/2))` 限速防刷屏。
- **跟随规则**：`scan_jobs()` 只取 `RUNNING`/`COMPLETING` 且 `job_gpus(%b) > 0`，
  按 `(GPU张数, 作业号)` 倒序取首个 → 训练占卡多就跟训练，保活占满 8 卡就跟保活，
  链式续期平滑换台。PENDING 一律不挂（`srun --jobid` 对排队作业会卡住）。
  `%b` 给 `gres/gpu:h100:8`，`job_gpus()` 解析尾段整数；解析失败按 1、无 gres 按 0。
- **`--jobid` 是锁定语义**：该 ID 不在 RUNNING 就一直干等，绝不偷偷换台。
- 新增 `--rescan`（默认 3.0，最小 1.0）—— 此前 `args.rescan` 被引用但**从未定义**，
  一进等待态就 `AttributeError` 崩。退避：`2.0*fails` 封顶 30s，fatal 时 `3.0*fails` 封顶 60s。
  `stale` 帧复用：收帧超时但有 `last_frame` 就继续显示旧数据并标 `⚠️ 数据停滞`，不刷错误行。
