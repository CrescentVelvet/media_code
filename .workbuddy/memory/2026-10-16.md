# 2026-10-16 工作日志

## 主题：D 案（稠密化自动调度器）冒烟 + 窗口后 prune 死亡螺旋的根因定位与修复

### 1. 症状

调度器 A 冒烟（double_wave，`USE_DENSIFY_SCHED=1`，激进参数 thr 0.0002/until 10000，
cap 600k，20k 迭代）**在 densify 窗口关闭瞬间崩溃**：
- iter 10000 首个「window closed prune-only」一步删 136k 点（599k → 463k）；
- 之后每千步 ×0.685 指数衰减 463k→286k→196k→135k→…→9.6k；
- PSNR 从 best 20.52@10k 崩到 @20k 5.34。
- **三次独立重跑完全一致**（20.472/20.504/20.517@10k 后同型崩溃）→ 可复现。

### 2. 诊断过程（带分量埋点，一次重跑拿全证据）

在 `_prune_mask` 里把三路判据拆开计数（opa / vs / ws）并重跑，关键数据：

| iter | opa(<0.005) | vs(max_radii2D>20) | ws(scaling>0.1·extent) | applied |
|---|---|---|---|---|
| 1000（窗口，size off） | 1668 | 0 | 12960 | 1668 |
| 4000（窗口，size on） | 439 | 994 | 994 | 1433 |

| 11000+（窗口关） | ~220 | 151886↑ | 1501↑ | — |

### 3. 根因（两条链都实锤）

**机制**：`densification_postfix`（fork `scene/gaussian_model.py:319`）在每次
densify（clone/split 加点）后把 `max_radii2D` **整体清零**。所以窗口内
`vs = max_radii2D > 20` 判据形同虚设（永远只看最近 100 步的新增量，≈0）；
**窗口关闭后不再 densify → max_radii2D 不再清零 → 单调累积成「历史最大屏幕半径」**，
第一个窗口后 prune 就把 ~137k「曾以 >20px 出现过」的点全删。

- 训练渲染用 `-r 2`（~960×720），单手近景时屏幕半径 >20px 的点占 ~23% 很正常，
  它们不是无效点，删掉必然塌模型。
- **正反馈（死亡螺旋）**：窗口后只剪不增 → 删点没有补充来源 → 剩余点被迫长大补偿
  覆盖面积 → 屏幕半径进一步超标 → 下轮再删。日志里 463k→286k→196k 的 ×0.685
  指数衰减就是签名。
- 对照组 `model_colmap_cap600k`（官方代码，硬护栏撞帽后整块跳过 = 窗口后完全不
  prune）@20k = 21.81 正常 → 证实问题就在窗口后 prune。

### 4. 修复

`sched_prune_only` 在窗口后调用处传 `max_screen_size=None`（**只按 opacity<0.005 剪**）：

- deformable_human/train_mask.py 窗口后分支（同款）；

  剪枝按 `max_screen_size` 决定是否并入尺寸判据）+ 自测第 11 组。

### 7. C3 隔离实验（窗口后 prune 是否该关）：**结论 = 维持默认 1**

C3 = `model_dsche_noprune`，与 C2 逐字同参（thr 默认 0.0007 / until 15000 / 调度器开 /
cap 600k / 20k / -r 2），**唯一差异 `DENSIFY_PRUNE_AFTER=0`**（窗口后完全不剪）。
目的：隔离「窗口后只剪不增」语义本身的代价（参考组同样不 prune，最可比）。

| 迭代 | C2（剪，prune_after=1） | C3（不剪，prune_after=0） |
|---|---|---|
| 18000 | 21.303 | 21.290 |
| 19000 | **21.549** | **21.557** |
| 20000 | 21.465 | 21.306 |
| 末三点均 | **21.439** | 21.384 |
| 点数@20k | 580,267 | 599,319 |

- Δ(末三点均) = **−0.055 dB**，@19k +0.008、@20k −0.159 → 全部落在三次重跑噪声
  ±0.045 量级内（@20k 的 −0.159 单点偏大但方向与 @19k 相反，判为噪声+次优快照）。
- 结论：**窗口后 opacity-only prune 对质量中性**，而 C2 少 19,052 点（−3.2%，
  N 减 → 步时随 N 线性下降）→ **维持 `DENSIFY_PRUNE_AFTER=1`**。
- 于是 −0.26~−0.34 dB 的代价**全部归因于「严格 cap 600k + absgrad 均值 topk 截断」
  策略本身**：参考组撞帽后整块跳过 prune、点数冻结在 629,715（超帽 4.95%），
  等于白拿 5% 容量且无 topk 排序偏置。→ 调度器默认仍关（保险丝按需开）。

### 结果（E 案 λ=0.05，严格同代码 A/B）：**负结果**

两轮逐字同参（double_wave/colmap_refined，20k，-r 2，thr/until 默认，调度器关，

|---|---|---|---|---|---|

| **Δ** | | **−0.527** | **−1.041** | **−0.530** | |

（FG/BG 由新工具 `03b_fg_metrics.py` 在 fg mask 内/外分别算；ALL PSNR 与训练期
`Evaluating test` 口径一致——已用 model_v1 逐位核对 14.038≡14.038。）

**判读：深度先验不仅没救手部，反而把前景砸得更狠（−1.04 ≫ −0.53 背景）。**

**根因（两条叠加）**：
1. **量级失衡**：深度残差是绝对米制（未归一化），实测 ~3.5~6.7，×λ0.05 =
   0.18~0.33；而光度项 EMA 只有 ~0.086~0.11 → **深度项是光度项的 2~4 倍，
   主导优化**（对照：λ=0 总 Loss ~0.09，λ=0.05 总 Loss ~0.33~0.52）。
2. **单目深度对手部不可靠**（BACKLOG E 案本就预警「快速运动小手部误差大」）：
   把逐点几何硬拉向错误深度 → 恰好伤在要救的部位。

**教训 / 后续方向（若要再做）**：
- 残差必须**尺度归一化**（除以对齐后的深度尺度，或用相对深度），否则 λ 随场景
  米制尺度漂移、不可移植；
- λ 应比现在小 1~2 个量级（0.005 起步）；
- 或换**边缘感知项**（只对 ∂d/∂x, ∂d/∂y 加 L1，对齐深度边缘而非绝对值）——
  这正是 BACKLOG 里的进阶变体。
- 当前默认 `DEPTH_LAMBDA=0`（关），代码与评测工具留仓备查。

### 9.5 ⚠️ E 案首跑踩雷：gy 镜像 bug 让深度损失全程静默失效（已修复）

**现象**：λ=0.05 那轮跑了 10k 步，`[DEPTH] enabled` 打了，但**没有一条**
`[DEPTH] iter N a=.. loss=..` per-step 日志 → 损失每步都返回 `None`，从没进梯度。

**定位链**（全离线，CPU）：
1. `DepthPrior.loss()` 只在成功时打印，失败原因被吞 → 先复现 None。
2. numpy 逐门限复现（run1 ckpt + train 相机 00001）：`in_frame` 22.4万点 ✅、
   `w_sum` 30142 ✅，**卡在 `gate align: a=-1.76 < 0`** → 每步被 `a<=0` 门限拦。
3. a<0 = 深度图值与 z_view 反相关。逐个变体测相关（`tmp_depth_corr.py`）：
   `gy=-ndc_y`（现码）corr(mono,z)=**−0.475**；`gy=+ndc_y` → **+0.677**。
4. **铁证裁决**（`tmp_gy_verdict.py`）：拿光栅化器自己渲染的深度图（投影真理，
   不依赖我手写投影对错），逐点算 corr(z_view, rendered_depth)：
   `gy=+ndc_y` = **+0.62~+0.88**（4 个测试视角），`gy=−ndc_y` = **−0.48~−0.50**。

**根因**：`depth_prior.py` 的 `gy = -ndc[:,1]` 照抄自 `deformable_human/train_mask.py`
的 `sample_fg_prob`（注释自称「qc_proj_fg.py 验证过」）。但本 fork 视图矩阵 y 轴
朝下（COLMAP）+ 投影矩阵 `P[1][1]=+1/tanfovy` 不翻转 → `ndc_y>0` 就是画面下半部；
grid_sample 的 `y=+1` 也是底部 → **正确约定是 `gy=+ndc_y`，不用取负**。

**当年为什么"验证通过"**：`qc_proj_fg.py:101-107` 把叠加点画在**与采样同一个
（可能翻转的）坐标系**里，点色=落点处 mask 值 → 任何 gy 符号下都「红点落在 fg
上」，对符号天然不敏感，**是无效验证**。

**修复**：
- `depth_prior.py`：`gy = ndc[:, 1]`（去负）+ 注释/docstring 更正。
- `train_mask.py sample_fg_prob`：同款修正（该函数只在 `bg_deform_lambda>0` 时
  调用，默认关 → **沉睡 bug，未影响既有实验**；被照抄到 E 案才真正发作）。

## B v2 结论：可微位姿精炼在 COLMAP 好初值上仍证伪（−8.29dB），路线收束

**配置**：hand_motion/colmap_scene，10k + warm 1000 + `-r 2 --densify_grad_threshold 0.0004
--densify_until_iter 2000`；两臂严格同参，唯一变量 `USE_POSE_REFINE`
（`model_bv2_ctl` vs `model_bv2_refine`：START=5000 / LR_WARMUP=2000 / ROT_ONLY=1000）。
点数 977,398 vs 975,449（−0.2%，排除容量差异）。耗时 1h40m（~3 it/s）。

| iter | ctl | refine | Δ |
|---|---|---|---|
| 5000 | 28.171 | 28.115 | 精炼刚启用 lr=0，持平 ✓ |
| 7000 | 28.496 | 22.657 | −5.84 |
| 10000 | 29.214 | 20.923 | **−8.29** |

**课程机制逐条按预期触发**（证明实现无 bug，是策略失效）：
- iter 5000 准点启用；启用前 drift 严格 0（新增的「启用前 drift」打印确认）
- iter 6000 放开平移；iter 7000 lr 系数拉到 1.00
- drift：rot 0→0.912° mean（max 2.324°）、trans 0→0.0140m

**根因（钉死在梯度方向，不是 lr 大小）**：
崩溃起点是 **iter 5100**——启用后第 **100** 步，此时 `scale_t=0`（平移仍冻结，
`lr_scales` 的 `scale_t = scale_q if k >= rot_only else 0.0` 已核对）、`scale_q` 仅 **0.05**。
loss 从 0.027 抬到 0.044（5200 到 0.090）。**纯旋转 + 满值 5% 的 lr + 100 步就崩**。
→ COLMAP 位姿已亚像素级准确，光度 loss 对位姿的梯度在弱纹理手部场景是纯噪声，
任何偏移都是净损失。

**reg 形同虚设（量化）**：`train_pose_refine.py:174` 确实加进了 loss，但
`reg_loss = delta_q².sum() + delta_t².sum()`，0.9° 旋转对应 delta L2²≈6e-5，
× `POSE_REFINE_WEIGHT=0.01` = **6e-7**，比光度项（~0.02）小 **4 个数量级** → 无约束力。

**结论**：三次证伪（v1 手机 VI 发散 14.78 / v2-a 手机 VI 延迟仍 16.35 / B v2 COLMAP 好初值
−8.29）合起来说明「可微精炼」整体不可用。位姿精化的正解是**离线 COLMAP 精化（01c/01d）**
——已实测同迭代数 **+7.29dB**。代码保留默认关（`USE_POSE_REFINE=0`）作负结果存档。
**（这条同时闭合了 BACKLOG B 案「验证第一步」的历史缺口。）**

## 14:30 评审：「99k 只需要改 gs_camera_params.json，还需要居中吗」→ **需要**

**峰哥的直觉有一半是对的**：`gs_camera_params.json` 里没有「居中」字段，而且 az/el/r 全部

**但"值对"≠"能用"**：下游把这三个量当「绕 **世界原点** 的球坐标」解释，原点必须落在主体中心——
- `99b:435` `view_limits["target"] = [0, 0, 0]` 写死；

## 15:30 「99k 为什么没有 THETA_TOP / THETA_BOTTOM」

**结论：不是遗漏 —— 两个脚本的职责方向相反，参数语义对立。**

- **99c = 收窄**：输入是 99b 已打包的 `view_limits`（**已有基准区间**），任务是往里收 →
  必须有**单侧**量；`crop_axis:214` `new_lo, new_hi = lo + cut_lo, hi - cut_hi`。
  `THETA_TOP/THETA_BOTTOM`（99c:545-546 读入 → 99c:241 传入），缺省取 `THETA_MARGIN=10`
  （`PHI_LEFT/PHI_RIGHT` 同理）；函数自带「收没了降级为一条缝」兜底（99c:207+）。
- **99k = 生成**：输入是原始采集位姿，区间**由数据边界给出**（`99k:434` `min(el)/max(el)`），
  没有可收的基准 → 只有一个**对称外扩**余量 `VL_EL_PAD`（`99k:439` `lo=min-pad, hi=max+pad`）。
  99k 里唯一「两侧分侧」的机制是 peak 的 `EL_PAD_GAP`（`99k:453-454`），但那是**分侧定 pad**，
  不是**分侧裁剪**。

**实测（佳佳蹲 68 帧，raw el [23.153, 32.794]）**：`VL_EL_PAD=-5` → pitch[28.153, 27.794]
**区间反转、且 99k 无任何保护**（99c 有缝兜底）→ 负 pad 不是可用的收窄手段。

**跨脚本换算法**：`Theta = 90 − pitch`（99b:431）→ `THETA_TOP` ↔ 抬高 `pitch_min`、
`THETA_BOTTOM` ↔ 压低 `pitch_max`。实测：THETA_TOP=10 → pitch[30.153, 35.794]；
THETA_BOTTOM=10 → pitch[20.153, 25.794]。

**若日后要在 99k 加收窄**：语义应设计成「从数据边界内缩」（如 `EL_TRIM_LO/EL_TRIM_HI`），
并把 crop_axis 的缝兜底一起移植；且**必须同步 99g**——99k 出图是调 99g、99g 自己重算区间，
不同步则图面约束与 json 对不上（README「99g 必须同步」已记此铁律）。
