## InfiniSplat v2 Step 2：同预算「加视角 vs 加分辨率」（commit 33a77b7）
- 设计：21v@777 与 48v@518 的 raw 几乎相同（9.68 vs 9.75M，差 0.7%），但**视角数与分辨率

  的方法论关键，先按 A/B 做会得出错误因果）。

  21v@518 4.26M / 14.6 GB / 26.1 s / PSNR 20.195 / σ1.50 / 锐度.686 / 双峰 27.6%

  48v@518 9.75M / 22.8 GB / 38.4 s / 20.457 / σ1.50 / 锐度.629 / 双峰 22.4%
- **统一到 392×518 后（11_budget_compare.py，GT 共用 + BOX 重采样）**：
  加分辨率 → PSNR **−0.28 dB**、锐度 **+12%**、双峰 −0.8pp（噪声内）
  加视角   → PSNR **+0.26 dB**、锐度 **−8%**、双峰 **−5.2pp**（27.6→22.4）
- **加分辨率不涨 PSNR 只涨锐度 ⇒ 多出来的高频与 GT 不对齐**（过锐/错位），不是真细节。
  加视角降重影的代价是更平滑：merge 丢弃率 4.7%→9.3%（重叠区被合并）。
  → 不是"谁更好"：要干净/准确选加视角；要细节/锐选加分辨率。

  单个并不更锐。⇒ **整图提分辨率低效（2.27× 预算买 1.2× 锐度），手/脸要锐只能 ROI 裁剪**。

  21v@777 原生 20.58 → 重采样 19.92，**差 0.66 dB 足以让结论反向**。

## 99m 视频编码改 H.264（commit 9c091d5）
- 峰哥反馈：99m 出的 mp4v（MPEG-4 Part 2）在 VSCode 里预览不了。
- 方案：不加独立转换脚本（峰哥明确「不用 99o、不管历史视频」），直接让 99m 出 H.264。
  BGR 帧喂 `ffmpeg -f rawvideo -pix_fmt bgr24 -i -` 管道 → libx264/yuv420p/faststart，
  **无中间文件、无二次编码损失**；cv2 只留作降级。
- ffmpeg 查找顺序：FFMPEG env → PATH → imageio-ffmpeg（pip 装，wheel 自带带 libx264 的
  静态 ffmpeg，免 sudo）。都没有则试 cv2 avc1（pip 版 OpenCV 基本不支持，实测报
  "Could not find encoder for codec_id=27"）→ 最后退 mp4v 并 WARN。
- 坑/细节：
  - H.264 yuv420p 硬要求偶数宽高 → `-vf pad=ceil(iw/2)*2:ceil(ih/2)*2`，奇数尺寸
    输出会大 1px（641x481 → 642x482，实测）；
  - ffmpeg stderr 必须落临时文件而非管道，否则报错刷屏会把 64KB 缓冲写满互相卡死；
  - 启动后 sleep 0.05 检查存活：参数错/无 libx264 时立刻失败 → open_writer 捕获后
    自动降级，不等到渲完几千帧才发现；
  - 编码失败要删半成品，否则 99n 的 SKIP_EXISTING 会把坏文件当已完成；
  - writer 接口统一成 write/close（原来直接调 cv2 的 release，第一版踩了 AttributeError）。
- 实测（本地 WSL，合成 1000 点 PLY + 60 帧 1080p）：h264 High/yuv420p/faststart ✅；
  耗时 1.8s vs mp4v 1.4s（编码开销约 0.4/60 帧），体积 163KB vs 334KB（约一半）；
  CODEC=mp4v / 奇数尺寸 / 无 ffmpeg 降级 三路都验过；抽帧目检画面正常。
- 服务器侧需要在 gs_traj_render env 补 `pip install imageio-ffmpeg`（README 已写）。
- 注意 commit message 规范：`git commit -F -` 的 heredoc 必须留标题与正文间的**空行**，
  否则 git 把整段当 subject（--oneline 显示成一行）。
