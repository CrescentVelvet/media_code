## 2026-11-06（夜）· P0 三项验证跑完，三项全判 B：瓶颈是跨视角几何一致性

台账：`compare_4methods/P0_EXPERIMENTS.md`（预测先写、实测后填，判据预先定义）
汇总图：`compare_4methods/ppt_assets/fig8_p0_evidence.png`

**统一口径**：全部 `REF_STRATEGY=first`（参考视角=帧0），PSNR/SSIM 是与输入帧的**自一致性**（非 NVS holdout）。

| 干预 | ΔPSNR | 结论 |
|---|---|---|
| 保留 SH rest @参考视角 | **+1.23 dB** | 外观容量只在几何对的地方兑现 |
| 保留 SH rest @其余 31 视角 | −0.25 dB | 外观容量不是主因 |
| 分辨率 504→1008 | −0.34（参考视角 −3.35，锐度 −29%，前向 7→282s） | 分辨率不是瓶颈，不重训就是负收益 |
| 视角 32→50 | +0.09 | 覆盖不足不是主因（转换器 n_views 上限 50，只能 1.56×） |

**关键机理发现**：DA3-GS 的质量随「相机中心到参考视角的三维距离」**单调衰减**——
0 m 处 20.8 dB，>0.5 m 掉到 10~11 dB，1.8 m 外 8/32 视角整片糊掉（Laplacian 方差 <20）。
说明它不是"不会做"，而是"跨视角不一致"。→ 计划调整：**P1 前馈 init + 3~5k 步短精调升级为首要动作**；
纹理头/双头继续后置；2DGS 原语维持最后（它不改位姿误差）。

**三个踩坑（已固化到脚本）**：
1. **DA3 世界坐标系由参考视角定义**，`saddle_balanced` 会随输入变参考帧（504→19、1008→31）。
   我第一版拿 504 的 npz 相机渲染 1008 的 PLY → 画面旋转错位、大片纯黑，白跑一轮。
   → `97_*.py` 现在每跑必落 `cameras.npz` + 支持 `REF_STRATEGY=first|middle|saddle_balanced`。
2. **千万级高斯的 full-SH 导出会 OOM**：24.4M × 41 float 走 `plyfile` 的 `list(map(tuple,...))` 要 ~10GB，
   整机被杀（SIGTERM、无报错）。加 `SAVE_FULL=0` 开关；以后千万级只导 DC-only。
3. **官方导出会剪枝**：预测 610 万 → PLY 实存 **484 万**（prune_by_depth_percent=0.9 + 边框剪枝）。
   fig3/PPT 里的高斯数已统一改成 PLY 实存口径。
4. gsplat 渲染的环境三件套（缺一就报 "No CUDA toolkit found" 或 "Ninja is required"）：
   `PATH=$CONDA_PREFIX/bin` + `CUDA_HOME` + `CPATH/LIBRARY_PATH=$CONDA_PREFIX/targets/x86_64-linux/{include,lib}` + `CC/CXX=conda-gcc`。

**汇报口径提醒**：fig1/fig6 用的视角 0/8/16 在 saddle 运行里离参考视角(19)有 11~19 圈，是该方法的**劣势视角**。
给领导讲时要同时给"参考视角"和"远离参考视角"两类，否则会低估/高估这个方法。

## 2026-11-06（夜·续）· P1 前馈 init + 短精调：判 B，加速来自"少跑步数"而非"前馈初值"

台账：`compare_4methods/P1_EXPERIMENTS.md`｜图：`ppt_assets/fig9_p1_tradeoff.png` / `fig10_p1_renders.png`

**结果（佳佳抱枕，32 视角，自一致性口径）**

| init | 点数 | iters | densify | PSNR | SSIM | 训练 |
|---|---|---|---|---|---|---|
| DA3 直出（不训练） | 484 万 | 0 | — | 11.38 | 0.268 | 0 |
| 前馈高斯 | 415 万 | 5000 | 关 | 20.14 | 0.728 | 466 s |
| 前馈高斯（剪枝） | 57.4 万 | 5000 | 开 | 21.72 | 0.763 | 169 s |
| DA3 点云 | 1.86 万 | 5000 | 开 | **22.23** | 0.738 | **123 s** |
| DA3 点云 | 1.86 万 | 30000 | 开 | **24.33** | 0.808 | 1253 s |

**结论**：PSNR 单调反比于初始点数。稠密高斯灌入反而更差且慢 4 倍。
根因：① DA3 的 opacity 中位数仅 **0.036**（25% 分位 0.013），大量半透明点既不达 3DGS 的
prune 阈值（0.005）也不会被合并，只能叠加成"糊"；② scale 中位数 **0.8 mm** vs extent 2.09 m，
过小椭球必须靠 clone/split 长回去，但 415 万点开着 densify 会吃满 24 GB，只好关掉；
③ 415 万点时 11 it/s vs 1.86 万点时 40 it/s，同样 5k 步付 4 倍时间。
→ **DA3 几何的正确接口是「稀疏点云 + 让 3DGS 自己 densify」，不是「整套高斯搬过来」**。
可用甜点：DA3 点云 + 5k 步，端到端 2.6 min / 22.23 dB（比 30k 少 2.10 dB，省 8 倍时间）。

**三个静默坑（无报错，全部踩过）**
1. **3DGS `restore()` 直接赋值 `self._xyz = model_args[1]`**，不包 Parameter。用
   `torch.from_numpy()` 存普通 tensor → requires_grad=False → autograd 不追踪 → 梯度恒 None →
   Adam 一步不更新。症状：训练正常打印完成、loss 在 0.30 附近"波动"（其实是随机相机差异）、
   存出的 PLY 与初值**逐字节相同**（四个 iteration 的 md5 全等）。ckpt 里必须包 `nn.Parameter`。
2. **`optimizer.load_state_dict` 整体重建 param_groups**：会覆盖 `training_setup` 刚设的
   per-group lr，并丢掉自定义键。ckpt 里的 `opt_dict` 必须(a)填真实 lr（否则 f_dc/opacity 等
   全组 lr=0 不学习），(b)补回 `"name"`（否则 `param_group["name"]` 直接 KeyError）。
3. **DA3 `export_to_colmap` 会原地把 `prediction.intrinsics` 放大到原图尺度**
   （fx 372→1417，1439/378=3.81×）。若在导出后才存 npz，拿去渲染 FOV 收窄、画面只剩局部，
   **看起来像几何错位**（白跑 200 步）。→ `98_da3_ff_init.py` 固定顺序：前向 → 存 npz → 再导出。
   另：3DGS `render.py` 的 `renders/{idx}.png` 用**渲染序号**、`gt/{image_name}.png` 用**图像名**，
   两者不是同一相机，不能按 sorted 索引配对。统一改用 94 渲染到 `view_N.png` 再比。

**新脚本**：`98_da3_ff_init.py`（一次推理同源出 gs_ply+colmap+npz，钉 REF_STRATEGY）、
`98b_ply_to_3dgs_ckpt.py`（PLY→3DGS .pth，含 SH 补齐 8→15、opacity/scale 空间、剪枝）、
`03b_train_short.sh`（短精调：等比压缩调度 + POSITION_LR_SCALE + DENSIFY 开关）、
`A1_make_p1_figure.py`（fig9/fig10）。

**matplotlib 在 WSL 画中文**：`rcParams["font.sans-serif"]=["Microsoft YaHei"]` **不管用**
（.ttc 按名字匹配不到），必须 `font_manager.fontManager.addfont("/mnt/c/Windows/Fonts/msyh.ttc")`

## 2026-11-06（深夜）· E-01：DA3 高斯漏乘度量 scale_factor，P0/P1 结论大幅修正

台账 `compare_4methods/ERRATA.md`｜对比图 `ppt_assets/fig11_e01_before_after.png`

**根因**：`da3.py:_apply_depth_alignment`（:400-415）只把 `depth` / `extrinsics` 乘
`scale_factor`（本场景自报 **1.9988≈2.0**），`gaussians.means/scales` 留在对齐前坐标系。
我们 97/98 把"官方导出的 PLY"与"米制 cameras.npz"混用 → 点云只有真实尺寸的 0.55。
DA3 自己知道这事：`export/gs.py:91-93` 渲视频时 `tgt_extrs[...,3] /= scale_factor`。

**为什么之前没发现**：缩放中心是参考相机（世界原点），径向缩放对针孔投影不变
（`u=fx·x/z`），所以帧 0 完全正常，只有其它视角横向错位 ≈0.45×距离。
实测逐视角自投影误差 1.19 px(v0) → 200 px(v16)，而 ‖means−深度抬起点‖ 恒为 ~0.9 m
—— **两个误差形态不同，是判定的关键**（只有径向缩放能同时解释）。

**修复后**（同一 PLY 同一相机，只差是否乘 2.0）：PSNR 11.38 → **18.97（+7.59 dB）**，
SSIM 0.268 → 0.577，锐度 149 → 222。帧 0 实测 **+0.07 dB**（预测"不变"，对上了）。
近远差距 3.31 → 1.42 dB，corr(距离,PSNR) −0.80 → −0.62 → **距离衰减真实存在但被放大 2.3 倍**。

**代码改动**：新增 `compare_4methods/da3_frame.py`（`gaussians_to_metric`）；
97/98 导出前折算并把 `scale_factor`/`gs_scale_applied` 写进 npz；
98b 读 npz 断言 `gs_scale_applied==1`（老 npz 直接报错，不做静默兼容）；
新增 `94_render.sh` 包装（gsplat JIT 要 conda 的 CUDA_HOME/CPATH/LIBRARY_PATH + PATH 有 ninja，
且**不能写 $CONDA_PREFIX**——wsl.exe 会把变量吃掉）。

**教训**：跨方法对比里"图看着不对"时，先算**同一套相机下自投影误差**，再怀疑模型能力。
这次 7.6 dB 的差距被当成"DA3 侧视角就是不行"，差点写进汇报。
