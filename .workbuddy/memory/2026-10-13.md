## 分辨率调度实测否决（A/B/C 探针，commit 54fe3a3）
- 带调度 20k 跑起来后瞬时速率从 5.6 掉到 1.9 it/s 且持续恶化（ETA 2.6h），主动
  pkill 停掉排查；加 `[DENSIFY]` 记账打印（每次稠密化打 thr/scale/点数，已留在
  train_som.py 作永久诊断）。
- **2500 步三探针**（double_wave，同场景同代码唯一变量是调度/补偿）：
  A 调度+补偿 thr÷scale → 418k 点/9:05/PSNR 13.28｜B 调度无补偿 → 323k/6:48/13.61
  ｜C 无调度基线 → 307k/6:45/13.56。
- **结论①零加速**（B≈C）：70% 迭代在 1/4~1/2 分辨率总耗时不变 → 瓶颈不是光栅化
  像素，而是随 N 线性增长的分辨率无关开销（SoM 系数场前向/Adam/稠密化记账）。
  参考方案「渲染便宜 4~16 倍」在渲染主导的栈成立，D-3DGS 系不成立。
- **结论②阈值补偿有害**（A 多 29% 高斯、慢 34%、PSNR 反低 0.33）：低分辨率下
  梯度分布变平，÷scale 放进大量冗余小高斯。量纲推导启发式被实测否决。
- 处置：代码保留（res_scheduler.py + train_som.py SOM-RES 注入），**默认关闭**
  （SOM_RES_SCHEDULE="" / RES_SCHEDULE=""），负结果写进 README 专节。
  真正速度杠杆 = 控制高斯数（densify 阈值），不是分辨率。
- 基线配置 20k 已重启（scheduler off），log train_20k.log。

## double_wave 20k 基线验收（10-13 午后，第一轮结论：容量不足欠拟合）
- 训练 20k 完成（~50 min）：test PSNR 14.04 / SSIM 0.335 / LPIPS 0.643，
  **PSNR 从 5000 步（13.96）起就平台期** → 非收敛问题，是容量瓶颈。
- 根因：沿用 hand_motion 的降载参数 `--densify_until_iter 2000 --densify_grad_threshold
  0.0004`，160 帧户外复杂街景只长到 216k 高斯；渲染时显存仅占 3.6GB/24GB。
- 抽图（test_00/10 GT vs render）：全图均匀模糊+细长条伪影，无区域性手部重影
  ——**欠拟合盖过了形变模型缺陷，手部验收指标不可用**。
- **重训计划**：`--densify_grad_threshold 0.0002 --densify_until_iter 10000`
  （预期 60 万–150 万高斯，训练显存经验 8–12GB，安全），其余不变。
- 修复 `render_som.py` MODE=original 崩溃（commit 2499c6a）：官方视角插值对 R
  做矩阵 lerp，相邻相机近 180° 时插值矩阵奇异（det=0，实测 cond 1.6e16）→
  四元数 SLERP（双重覆盖取短路径），200 组随机旋转单测全过。**官方代码同源 bug，
  只在大角度环绕采集场景触发。**
