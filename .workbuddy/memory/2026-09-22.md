## Remy（鸿蒙 3D 采集 App）数据格式分析 —— transforms.json

样本：`D:\dataset\测试数据sample\13a8ecadfeb448e890db319ac828befe\transforms.json`

结论（已实测核对）：
- 采集端 = 华为/KIRI 的 Remy（HarmonyOS 独家的 3D 空间记忆 App，pcd.ply 头部有 `comment Created in Remy`）。
  位姿来自 AR Engine VIO，**自带米制尺度 + 重力对齐**，不是 COLMAP SfM 估计的。
- 目录三件套：`image/`（155 个 .heic，1440×1920）+ `pcd.ply`（191078 点，binary LE，15 B/点，xyz float32 + rgb uint8）
  + `transforms.json`。file_path 与磁盘文件名一一对应（已核对）。
- 顶层：version=1 / platform=Harmony / platform_version / capture_mode=1 / camera_model=OPENCV
  / anchor_point=[-4.171,-2.271,-0.617] / ply_file_path / frames[155]。
- **transform_matrix 是 camera-to-world**（已证：第 4 列 = 相机光心，各帧到 anchor_point 水平距离恒 0.81–1.08 m）。
- **相机前向 = −Z（OpenGL/Blender 约定），不是 OpenCV 的 +Z**。证据：look = −R[:,2] 与 (anchor − C) 的 cos 均值 0.9926；
  按 +Z 为前向则 cos = −0.9926（背对锚点，不可能）。`camera_model:"OPENCV"` 只描述畸变参数集（k1,k2,k3,p1,p2），
  不描述外参轴向 —— 这两件事容易混淆，踩坑点。
- 世界系 +Y 向上（重力对齐）：相机 +Y 轴在世界 Y 的分量均值 0.889（min 0.805 / max 0.984）。
  → 不是 nerfstudio 默认的 Z-up，走 nerfstudio 系要处理 orientation。
- 内参 155 帧完全一致（唯一组合数 = 1）→ 单一标定，非逐帧估计。
  w=1440 h=1920 cx=716.07 cy=952.97 fl_x=1359.49 fl_y=1361.67；k1=0.0909 k2=-0.2374 k3=0.1914 p1=-2.1e-4 p2=8.8e-4。
  等效焦距 ≈ 24.5 mm（35mm 制），短边 FOV 55.8° / 长边 70.4° / 对角线 82.9°。
- 帧文件名 = 15 位纳秒时间戳（自开机），跨度 16432746999 → 16.43 s，等效 9.37 fps。
- pcd.ply 点云 bbox 2.74×1.39×2.43 m，与相机同处一个米制世界系。

未核实/待确认：capture_mode=1 的确切含义（推测"物体环绕"模式）；platform_version 里 SGP 字段（推测区域码）；
SGT-AL10 对应的机型名。

对 pipeline 的影响：需要 HEIC 解码（pillow-heif / ImageMagick）；需去畸变；尺度无需再对齐。

## 新增 vggt_human/99g_plot_capture_trajectory.py（commit e998922）

把每个采集 ID 的 transforms.json 画成自包含 HTML（内联 SVG），图内标题与文件名都用文件夹 ID。
纯标准库（json/math/struct），服务器 / WSL 都免装依赖。四种风格：`minimal`（浅色极简）/
`darkspace`（深色网格 + 时间渐变）/ `fov`（视锥扇形 + 点云底图）/ `iso`（等轴测含高度）；
`STYLE=all` 一次出全部并生成 index.html 总览页。用法已写进 README_wsl.md。

实现要点（踩过的坑）：
- 图例横排必须按字符宽度估宽：CJK 1.0em、ASCII 0.55em；用 0.55em 统一估会让相邻项重叠。
- View 类两轴共用一个 scale，否则轨迹被拉扁；半径环 / 点云要 clip 到绘图区，否则溢出到页面。
- 点云 bbox 必须用全量点统计（抽稀后算 bbox 会把极值点抽掉，2.74→2.70 m 这种偏差）。
- anchor 水平距离要用 (X, Z) 不是 (X, Y)：写错会让均值半径环画错（0.74 vs 正确 0.90 m），
  且统计卡片跟着错 —— 这类「看似正常的错值」只能靠与独立计算对表发现。

验证方式：用无头 Edge 截图（`msedge --headless=new --screenshot`）逐张看图核对，
比只跑脚本看退出码可靠得多。

## 99g 追加 combo 双联图风格（峰哥选定的最终版）

需求：一张图里两幅 —— 左「等轴测（含世界 Y 高度）」+ 右「俯视图（世界系 XZ，浅色 + 轨迹按帧序时间渐变）」。
已把 `STYLE` 默认值改为 `combo`，另加独立 `.svg` 输出（每个风格同时落 HTML + SVG，SVG 可直接进 PPT）。

做法：把两个视图的几何抽成公共函数 `draw_top_geometry(view, ramp=...)` 与
`draw_iso_geometry()`，`minimal` / `iso` 也改为调用它们（消除重复）；等轴测投影提到模块级
`iso_proj()`。浅色底的时间渐变用 RAMP_LIGHT（#1D4ED8 → #7C3AED → #DB2777），
深色底用的是青→紫→玫红，白底上太浅。

布局踩坑（都是截图后才发现的）：
- **图例/脚注不能硬编码 x**：View 按数据长宽比居中留白，绘图区左边界随数据变，
  硬编码会让图例和脚注随数据错位、互相压字。改为用 `view.rect()` 的实际左边界对齐。
- **比例尺要画在绘图区内部**：放外面时，0.5 m 的像素长度随比例尺变化 + 右栏整体右移，会顶出画布。
  同理两个脚注合并成底部一行，避免右栏那行被裁。
- 两栏绘图区按各自数据长宽比给尺寸（左 640×400、右 380×400），否则内容被塞进大片空画布。
- 顺带修掉颜色歧义：末帧标记原来是琥珀色，与 anchor_point 同色，改成玫红 #BE123C。

## combo 第三轮：图放大、图例摊开、消空白（峰哥：「图可以画大一点，图例分散一点，不要留太多空白」）

三条手法：
1. **绘图区尺寸按各自数据长宽比反推**（`top_h = TOP_W/aspect`，`iso_h = ISO_W/aspect`，各带
   clamp），而不是给个方框让 View 自己居中——等比例缩放下预留框比例不对就必然留白边，这是
   前几版空白的根因。画布高度随之动态累加（`out[0] = svg_open(W, H)` 最后回填）。
2. 画布从 900×1010 收到 760×~1150：画布越窄、内容占比越高，在 HTML 列宽固定的情况下
   显示得越大（scale = 列宽/画布宽）。俯视图 400×470（原 327×380，屏显约 +45%）。
3. 图例摊开到空出来的位置：俯视图右列竖排（行距 36，并在列内竖向居中）+ 时间色条；
   等轴测下方 2 行 × 3 列网格。

另外修了一个更实质的问题：**等轴测视野不能用点云范围**。ID 3fe0604320 的点云 bbox 是
3.71×2.14×4.87 m，而相机轨迹只有 1.18×1.74 m，全算进视野后轨迹被压成角落一小团。
新增 `iso_extent(ctx)`：视野 = 相机 + 锚点 + 相机落地投影，点云只作背景、超出部分由 clipPath 裁掉；

`-Encoding UTF8` 读 + 按字节写，或改走 Python。

## 99b 反推 yaw 取负修正（commit d462b23，峰哥给的正负号方案）

背景：99b `generate_uwa_jsons` 的放置式是 `loc = [-vx, vy, vz]`（vx=sin(yaw)θ, vz=cos(yaw)θ），
实际放置方位角 = atan2(-vx, vz) = **-yaw**（X 轴镜像）。所以凡「从相机位置反推出 yaw」的地方
都必须取负，放置点才会落回该位置本身。

改了两处（各 +2 行注释）：
- 行 405（GS_FALLBACK 分支）：`yaws.append(-math.degrees(math.atan2(pv[0], pv[2])))`
- 行 447（init_camera 块）：`yaw_init = -math.degrees(math.atan2(p0[0], p0[2]))`

**刻意没改**（峰哥指定）：view_limits 块（直接拷 gs json 的 yaw_min/yaw_max）、insideout 分支
（行 449-451，在取负之后执行，属独立变换）、所有 pitch 代码（Y 轴无镜像）、行 479-481 的
pitch_init 交叉校验。

验证（临时脚本 `%TEMP%\verify_99b_yaw.py`）：ast.parse 通过；全仓「未取负的 atan2-yaw」计数 = 0；
用 4 组手算点位跑 pos→(pitch,yaw)→loc 往返，最大误差 4.44e-16（旧写法在 p=(1,0.5,2) 得 (-1,+0.5,+2)，
即镜像位置，确认是符号 bug 而非插值误差）。

连带确认：99c `pos_to_pitch_yaw` 用的是 `atan2(-x, z)`（= 正变换的严格逆），且它反解的是
init_camera 的 **position 字段**而非 yaw_init，所以 99c 一直是几何正确的 —— 99b 修好之后
两者的角度约定才真正对齐（此前 99b 写进去的 position 是镜像点，99c 反解出的是那个镜像点的
真实几何角，口径一致但位置本身错）。
