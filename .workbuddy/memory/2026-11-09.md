## I-03b：把 2DGS 的盘法向换成 oracle（GT 深度法向）→ H2 证伪，2DGS 路线终止（09:45）

**动机**：I-03 把 2DGS 更糊归因于「DA3 的盘法向没有几何意义」。该结论可检验且不需重训 ——
直接把旋转矩阵第三列换成 GT 深度图的表面法向，其余一个字节不动。

**做法**：同一 PLY（`i12_fullpts_sh` 610 万点·全 SH·官方 22.11 dB）、同相机、同 `sh_degree=2`、
同轴序约定；三档 2DGS 之间只差第三列。法向采样过一致性闸门 `|Δz|/z<3%`，
单视角命中 25.1%、至少一处 65.1%、平均命中 12.35 视角，**34.9% 回落重排法向**（比例已报出）。

**结果（32 视角）**

| 档 | 全图 | 人脸 | 锐度 | 人脸锐度 |
|---|---|---|---|---|
| 3DGS EWA（原版 DA3-GS） | **22.11** | **20.00** | **398** | **347** |
| 2DGS 重排（I-03） | 21.82 | 19.64 | 331 | 342 |
| 2DGS oracle（每点唯一） | 21.40 | 18.84 | 320 | 329 |
| 2DGS 逐视角 oracle（上界） | 21.11 | 18.88 | 321 | 319 |

判据 J-PSNR / J-FACE 全 ❌（−0.72 / −1.17），前提闸门覆盖率 65.1% ✅。
**法向净贡献 −0.43 dB（全图）/ −0.81 dB（人脸）。连"逐视角上界"都没追回来。**

**三个替代解释同时被证伪**（各有独立脚本，这点比结论本身更值）：
- H-厚度：`s_min/s_mid` 中位 **0.0000**，98.37% < 0.05，`s_min` 中位 0.000 mm → 确实是薄盘。
- H-覆盖：三档 α 中位 0.9999、均值 0.9957/0.9916/0.9904、α>0.5 恒 100% → 覆盖没变薄。
- H-足迹：2DGS 的 `eps2d` 三档（0.3/0.1/0.01）**读数逐位相同** → 该参数在 2DGS 路径被忽略；
  而 3DGS 侧高度敏感（0.3→0.1 锐度 412→472，0.01 崩到 21.39）。

**口径订正（本轮最贵的教训）：人脸窗**
`audit_14` 起沿用固定框 `(0.35,0.105,0.565,0.335)`，而人头位置逐视角差很大：
view 0 x 168~212、view 8 x **218~268**、view 16 x 178~235。旧框在 view 8 落在**书架**上，
于是：
- 人脸基线 19.72 / 锐度 489 作废 → 真实为 **20.00 / 347**（虚高 +180）
- I-03 的"人脸锐度 −69" → 实际只有 **−5**（夸大 14 倍）
- §2.5 的"全 SH 只买清晰度、不裁剪买准确度"要改写成：**全 SH 两头都赚（PSNR +1.12、锐度 +129），
  不裁剪只赚准确度（人脸 +1.04 / 非人脸 +1.70、锐度 +5）**
已加闸门：区域指标第一次报数前必须目视裁出来的图（ERRATA E12）。

**决策（用户指示"效果不好就改回原版 DA3-GS"）**：
1. 正式口径 = 3DGS EWA + 官方等价导出（不裁剪 + 全 SH），22.11 dB / 人脸 20.00 / 锐度 347。
2. **I-04（改头 + 法向正则，重训）撤销** —— 收益假设建立在"法向是瓶颈"上，已证伪。

   时当深度估计器用，不拿来替换渲染器。
4. 改进方向转到点数 / σ / 训练策略。
5. **代码从未把 2DGS 接入交付链路**（都是独立审计脚本），"回归"不需要回滚生产代码。

## da3_human：C-06 双分支 2DGS 路线终止（10:20）

**触发**：峰哥质疑「PSNR 15.2、跑 1 小时，DA3 高斯头本来是秒级」→ 复核确认 06 是双输。

**决定性对照**（同一份 DA3 几何、同场景 125 视角 1440×1920 in-sample）：

| 配置 | init 点 | 最终点 | 步数 | 训练 | PSNR |
|---|---|---|---|---|---|
| 官方 DA3-GS 直出 | — | 1891 万 | 0 | 203s 前向 | 17.93 |
| 06 v3 anchor+2DGS | 683,879 | **683,879（不动）** | 30K | 3,779s | 15.209 |
| **P1 DA3稀疏+3DGS** | 18,057 | **616,420（densify）** | 5K | **461s** | **23.79** |
| 04 DA3点云+3DGS | 459,433 | ~500 万 | 30K | ~3,600s | 25.505 |
| 03 COLMAP+3DGS | 7,163 | — | 30K | 2,751s | 27.573 |

**核心结论**：最终点数 68.4 万 vs 61.6 万几乎相同，PSNR 差 **+8.58 dB**、耗时差 8.2 倍。
⇒ **densify 决定的是「点的质量分布」而非「点的数量」**——这是本次最可复用的认知。

**06 的四个可定位缺陷**（`06_train_da3_2dgs.py`）：
1. 完全没有 densify（L106 `M = len(xyz)`，五个参数全 `(M,·)`）→ 30K 步一个点没长；
2. 有界 offset 焊死错误初值（L119-121 ±1px/±2%，L164 `LR_GEO=1e-4`），而 B-04b 已证
   DA3 深度噪声是主因 —— 等于明令禁止修正；
3. 每 iter 从磁盘读图（L217，无缓存）→ 1440×1920 JPG 逐帧解码；
4. 每 iter 两次全量光栅化（L225 全分辨率 + L236 1/4）。
   但单步并不慢（04 是 120ms/it，06 是 126ms/it），慢的是 **30K 步全在做无用功**。

**避免错误归因**：2DGS 不是元凶（compare_4methods I-03：同 PLY 同相机只换光栅器仅 −0.29dB）。
2DGS 只保留 `median_depth` 掠射一致性用途（0.41% vs 3DGS 0.80%），不做外观主链。

**判定**：C-06 终止（负结果封存）；「DA3 几何 → 稀疏化 → 3DGS + densify」确认为主链；
05 的 683,879 anchor 降级为几何分析/初始化候选。已提交 `750d901`。

**复现**：`ITERATIONS=5000 MAX_INIT_POINTS=20000 SCENE_DIR=.../da3_colmap_scene_p1
GAUSSIAN_DIR=.../p1_da3sparse_5k bash da3_human/04_run_da3_gs_baseline.sh`

**待定下一步**：扫 MAX_INIT_POINTS{20k,50k,200k}×ITER{5k,10k} 找拐点（04 说明还有 1.7dB 空间）；
补留出视角 NVS 口径（当前 125 视角全 in-sample）。

**工程坑**：`wsl -d Ubuntu2404 -- bash -lc '...$VAR...'` 变量会被吃掉 —— 路径一律写字面量。

## 四方法对比的三张 PPT 图 + PLY 环视视频（10:20）

**结构定型（峰哥纠正过一次）**：主角是 **DA3-GS = DA3 原生高斯头**（13.5 s 一次前向），
不是「DA3 接 3DGS」。QuerySplat(38.5 s) / InfiniSplat v2(3.3 min) 同档；
两个 +3DGS（20.4 / 22.9 min）只作「多花 100 倍时间买到什么」的参照。

三张图：
- `fig33_method_matrix.png` 5×6 机制矩阵（几何来源/高斯来源/是否逐场景优化/规模/耗时）。
  口径纪律：**只给 DA3-GS 标 PSNR**，其余四方法没在同一批相机上重渲染，跨口径排名是错的。
- `fig34_time_compare.png` 分段横条 + 秒级放大插图。13.5 s 在 1400 s 尺度上是一条细线 —— 这就是结论。
  前馈只占两根长条的 2.5%。
- `fig35_showcase.png` GT + 5 方法 × 视角 0/16。参照两列轻降饱和 25%（先用 45% 太狠，
  会被读成「质量差」而不是「配角」）。

**环视视频踩的三个坑（都写死成自证了）**：
1. **视向符号**：DA3 外参是 COLMAP 惯例（看向 **+z**）。按 OpenGL(−z) 算，整条轨道反 180° →
   画面全是书柜窗帘、人在背后。
2. **注视点**不能用相机中心均值（偏 0.855 m），要用 32 条视线的**最小二乘交点**。
   验证很硬：沿各自视线走 1.5 m，落点离散度 **0.093 m**（方向错则 >2 m）。
3. **手性**：`x = forward × up`，不是 `up × forward`。

三道自证：指向交点 vs 真实视线 **1.97°**；`look_at(C[0])` vs 真实外参 **2.88°**；
环法向 vs 相机 up **14.35°**（残差来自 23.6° 俯仰，反向会是 ~166°）。
轨迹也不另造圆，直接沿真实相机位置的方位角插值 —— 相机一定落在采集轨迹上。

**最重要的发现：32 视角不是完整环绕。** 方位角只覆盖 **252.7°**，
−147.4° → −40.2° 之间有 **107.3° 没有任何观测**，且分布不均（最小间隔 0.18°，中位 7.1°）。
360° 视频转到缺口就出现横向条纹拖影 —— 不是渲染 bug，是 PLY 里没那块数据；
`ARC=1` 只在观测弧上走，全程清晰，两版对照即证。
→ 已落成 `audit_23_coverage.sh`，结论进 ERRATA E15 + FINDINGS §2 警告。
**PPT 里讲「32 视角」必须补一句「约 253° 的弧」。**

## 五方法同轨迹对比视频 + QuerySplat 画幅订正（2026-11-09 第二轮）

峰哥要求：fig35 里 QuerySplat 不要正方形（其它列都是 3:4）；再出一支**五方法同一相机轨迹**
的对比视频，轨迹用 252.7° 观测弧。

**跨方法同轨迹的前提是先搬到同一坐标系**（`audit_24_five_way_video.py`）：
- DA3-GS 是 metric（is_metric=1），QuerySplat / InfiniSplat v2 / VGGT+3DGS 活在 VGGT 系，
  Umeyama 出 **s = 2.25 ~ 2.28**。不校尺度就只是"五个视频各绕了一圈"。
- 对齐后残差 0.27~1.03% 半径、视线 0.11~0.46° —— 残差量级本身就是可信度证据。
- **3DGS `cameras.json` 的 `rotation` 存的是 c2w**（forward = 第 3 列）。按 w2c 读（第 3 行）
  视线夹角 97.6~106.2°（几乎正交，错得很明显但要四种全试才能定）；改列后 0.11~0.25°。
  → ERRATA E16、E17。
- 渲染必须**逐个方法载入→渲完→释放**：五个 600 万点同时常驻，24 GB 卡在第三个方法上 OOM
  （isect_tiles 申请 12.78 GiB）。逐个跑峰值 2.3 GB，全片 90 s。
- 首版读 PLY 漏了 `np.exp(scale_)`（传进光栅器的是 log 尺度 −6.28），导致同样的 OOM。
  两个 OOM 原因不同，别混为一谈。
- `TRIM=0.05` 两端各内收 12.6°：缺口边界最近的相机是斜视的，末帧 VGGT/DA3+3DGS 的窗帘会拉成
  黑白条纹。实际扫过 227.4°，仍在观测弧内；要完整弧设 `TRIM=0`。

**QuerySplat 的"正方形"不是几何压扁，是画布**（`audit_25_qs_aspect.py`）：
- 它的 K 是 fx≈fy≈494、cx=cy=256（512² 画布）→ 方形像素、方形视场，**垂直只到 54.8°**，GT 是 68.6°。
- 四方案 PSNR（v0/v8/v16 三视角投票）：A 原样 512² **11.95**｜B 只压横 0.75 **11.96**｜
  C 中心裁切 **11.22**｜**D 焦距等比缩 0.75 放进 3:4 = 16.55**（v0 单视角 21.63）。
- 关键教训：B 几乎与 A 相同 → "压扁"假设被自己的判据否掉。**改完 PSNR 动不到 2 dB 就是方向错了**。
- 正确解 D：像素保持方形，fx=fy=f_norm×W（0.966×540=521.4），垂直视场自然张到 69.2° 与 GT 对齐。
  → ERRATA E18。32 张 540×720 图在 `querysplat_results/佳佳抱枕_paper/rendered_34/`。

不是 degree 3 —— 之前 "全 SH" 的说法指"全量导出该阶"，别读成 3 阶。
