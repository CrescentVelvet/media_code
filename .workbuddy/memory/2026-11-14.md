# 2026-11-14

## canada_h100：新增 13_gpu_watchdog.sh 显存看门狗（cron 每 2h）

峰哥说明 `sa_train` 作业的真实目的是**占住卡避免空置被管理员骂**，训练日志不用看，
只需要盯显存。据此新增 `canada_h100/13_gpu_watchdog.sh`，装进服务器 crontab 每 2 小时一次，
掉了自动 `12_sa_train.sh start` 拉起。

判据只有一个：卡上有没有显存占用。作业名/loss/step 一律不看。七种判定：
OK（≥30% 显存）/ WAIT（低于阈值但未过 10m 宽限）/ BAD（低且过宽限→stop+start）/
PEND（有排队不重提）/ EMPTY（空卡→start）/ UNKN（srun 取样失败→不动手）/
BOOT·FAIL（拉起成功·失败）。阈值走 `WATCHDOG_MEM_MIN` 等环境变量。

七个分支全部用桩脚本实测过（不打桩会误杀真作业）。

**两个坑，别改回去**：
1. **`srun` 把 PATH 透传进计算节点**。cron 的 PATH 比登录 shell 窄，`env -i` 下为空，
   报 `execve(): nvidia-smi: No such file or directory` —— 看着像作业坏了，其实是找不到命令。
   已显式兜底 PATH + `nvidia-smi` 用绝对路径 `/usr/bin/nvidia-smi`。
   这个坑第一次误判成 UNKN，靠 `env -i` 对比才定位。
2. **`scancel` 后作业先进 `COMPLETING` 仍挂在 `squeue`**，此时 `12_sa_train.sh start`
   会以「已有训练任务」拒绝提交，形成「旧的杀了、新的起不来」的空卡窗口。已加最多 90s 等队列清空，
   等不到就放弃本轮。第一版没这逻辑，测试第 8 场景 15s 就放行才暴露。

另有 scp 静默失败一次的教训：改完脚本先 `md5sum` 两边对比，别信 scp 的退出码——
那次传送失败导致服务器跑的是旧版，测试结果对不上查了半天。
