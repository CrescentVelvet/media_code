# 2026-09-29 — minimax_h3 出噪点排查（第二轮，范围收窄）

## 峰哥提供的关键新事实
**服务器上跑 minimax 全量版 + int8 版都干净，只有本机 WSL 出马赛克。**
追问确认：服务器跑的是 **同一套 diffusers 06x 脚本**，**单卡 80GB**。
→ 模型 / 权重（服务器份）/ 量化 / LoRA / pipeline 代码 / scheduler **全部出局**，
   只剩本机环境。但单卡 80GB 也放不下 66G transformer + 63G text_encoder，
   **所以服务器照样开着 offload**（只是 CPU 内存远大于本机 54GB）。

## 本轮逐个排除的（都有实测证据，不是推理）
| 嫌疑 | 实验 | 结论 |
|---|---|---|
| offload 机制 | tiny fixture 四配方 A/B：常驻 / `block_level`+`use_stream` / CM auto offload | **全部逐元素 max\|Δ\|=0**，`.pt` 存档 `z_*.pt`/`x_*.pt` 于 temp；onload 时刻权重与 CPU 母本差 **0.000e+00** |
| torchao int8 | 512×256 Linear，per-channel 尺度差异 4× | v2/v1 相对误差 5.8e-3，逐通道 0.0039–0.0086，**0/256 通道 >5%** |
| C++ 扩展缺失 | `torch.ops.torchao._weight_int8pack_mm` 不存在、`intmm` 可导入 | 只是走后备 kernel，**数值正确**，不是问题 |
| scheduler | 不加载权重直接读 | sigma 网格是 **shift 变换过的**（非 `linspace(1,0,N)`）；快照默认 `shift=12.0`；`set_timesteps(51)`→51 sigmas/50 steps，尾部 0.4337→0.3333→0.1967→0；**约定正确** |
| CFG / guider | `denoise.py:55-56` 原文 | H3 是 **guidance-distilled，无 unconditional pass、无 guider** |
| LoRA alpha | 昨日已修 | 确证 bug：v1.2 / 8step_768p 的 alpha=8 被写死 128 → 放大 16× |

## ⚠️ 推翻两个旧结论（重要）
1. **09b 不是"纯 bf16 无 int8"**——它源码里就是 `TorchAoConfig(Int8WeightOnlyConfig(version=2))`
   加载 transformer 和 text_encoder。之前基于"09b 是 bf16 基线"的推理是错的。
   真正证明"bf16 也坏"的是 **06b**（无量化，走 ComponentsManager）。
2. **09d「零结构噪声」的判读是错的。** 重算 `latent_decode1.pt`：
   - `z shape = (1, 24, 37, 34, 60)`，整体 std=3.47 vs RMS(latents_std)=1.925（1.80×）
   - **空间 lag-1 自相关 +0.782 / +0.786，帧间 lag-1 = +0.796** → **强结构，不是白噪声**
   - 各通道 mean 的抽样 z 分数 **+81 ~ +519**（纯噪声应全在 ±3 内）→ 系统性逐通道 DC 偏移

## 本轮最硬的一条实测（新脚本 `latent_vs_noise.py`）
把 raw latent 反归一化回归一化空间，与"重放 seed42 CPU generator 的初始噪声"比：
**corr = +0.445**。
判读已被源码证实：`before_denoise.py:847-850` 明确"conditioning noise 先抽 → **再抽 video
noise** → 再抽 audio"；09b 是 t2va（无 conditioning），`:853` 的调用
`randn_tensor((1,24,37,34,60), generator, device, dtype=float32)` 与重放参数**逐项一致**。
→ **50 步跑完，最终 latent 里仍留着 44.5% 的初始噪声 = 去噪没有收敛**。
这不是"噪声"，是"模型的速度场没在干活"。

⚠️ 但我随后意识到：这个 0.445 无法区分「模型输出错」和「依赖同一随机数」——
两类成因（权重坏 / 数值坏）都会给出高残差。**它只证明"未收敛"，不指认凶手。**

## 本机环境侧发现
- **另一个 worker 正在同仓并行作业**：`09f_check_text_encoder.py`（未跟踪，09:40 建，
  PID 369 跑着，VmRSS 34G / VmHWM 55.6G / 占 4.7G VRAM）；同时 06b/06d .sh、
  `_turbo_lora.py`、README 在 09:48–09:53 被改动（**不是我改的**）。
  → 结论：本仓此刻**有并发写入**，改仓库文件前必须先确认，否则会互相覆盖。
- **内存枯竭**：MemFree 1.6G / 56G，`Node 0 Normal free:52876kB` 已跌破水位线
  （min:48072），swap 128G 几乎没被用。后果：`dd` 与 `sha256sum` 读 /mnt/d
  **报 `Cannot allocate memory`**，造成 sha256 校验出现**假 HASHBAD**（`local=` 为空串）。
  单独重跑即与 HF 期望值一致。
- 权重完整性（对 HF LFS sha256）：audio_vae ✓、text_encoder 00001/00002/00004 ✓，
  全文 32 个文件的校验被并发负载打断，未跑完。
- **09f 的"text encoder std 爆（51/219）"是测量假象**：prompt fox 16×5120 元素，
  单值 14528 的 RMS 贡献 = 14528/√81920 = **50.8**，正好等于实测 std=51.30；
  prompt "a" 1×5120 → 14912/√5120 = **208.4** ≈ 实测 210.4。是 LLM 已知的
  **massive activation**，不是数值损坏。同理 `cos(fox,"a")=0.99` 是 mean-pool
  被巨激活维度主导的假象，不能当"无视 prompt"的证据。

### 对 vggt_human 主线有用的结论

- **按"视频生成模型在链路中的角色"切成六条路线**：A 多视角视频生成→4DGS（主战场）、B 潜空间直连 4D、
  C 生成当补全/伪监督、D 视频扩散当 SDS、E VDM 当确定性几何编码器、F 纹理空间生成动态外观。
- **2026 年的分水岭是上下文工程**：DiT 单次前向能容纳的目标视角数有上限，超限必须分组 → 参考侧 O(N) 膨胀 +
  目标侧组间结构漂移（4DAnyone 的 bounded-attention-context 诊断）。四种解：RCP+TCR（4DAnyone）、
  滑动迭代去噪（Diffuman4D）、级联解耦（4DVD）、历史 token rollout（Flex4DHuman）。
- **单卡 3090 可行性排序**：Flex4DHuman（Wan2.1 **1.3B**）> Diffuman4D（有 `demo_4d_tiny` 小配置）>
  4DAnyone（Wan2.2-TI2V-5B，原训练配置 128×H20-3E，单卡必须分组降采样）。
- **条件信号我们全有**：COLMAP 位姿 + MHR 3DMM + SAM3 mask + ExpTracker 657 点 landmarks →
  正好能拼出 Diffuman4D / 4DAnyone 需要的"骨架 + 相机"条件，**骨架条件路线改造成本最低**。
- **若"固定表情系数消除微动"是主要矛盾**：路线 C 的人机分工（StudioRecon：扩散只补背景，人体走几何 +
  关键点三角化初始化）比端到端生成更可控，不会把生成的身份漂移引进人脸区域。
- **警示**：生成视频 PSNR ≠ 4DGS 重建质量；4DAnyone 的 24.33 dB 是重建后渲染指标，且其自认短板是
  真实无控场景（DyMVHumans 21.03 dB << DNA-Rendering 24.33 dB）。
