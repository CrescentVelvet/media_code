## MiniMax-H3 单卡 3090 复现（media_code/minimax_h3）— 彩色方块噪点排查

### 结论：可行性
- 推理复现可行：diffusers 官方文档有专门的「consumer card (24–32 GB)」配方（int8 + streamed
  block offload）。需 ~75GB 主机内存（int8 下），用户 64GB RAM + 128GB swap 勉强够但会大量走 swap。
- 训练/微调复现不可能（33B transformer + 32B Qwen3-VL 编码器）。
- 3090 是 Ampere(sm86)，`_flash_3_hub`（Hopper 专用）用不了，需用 sdpa / flash-attn2。
- VAE 是 fp32 且 10.42GB，audio_vae 0.61GB，常驻 GPU 后 24GB 里固定占掉 ~11GB
  → 768p(1344×768) 解码大概率 OOM，必须降到 960×544。

### 本地快照核查结果（D:\wheel\minimaxh3_ms，ModelScope 来源）
- transformer: 33.123B params / 66.28GB，626 个 BF16 + **12 个 F32**
  （proj_in/proj_out/audio_proj_in/audio_proj_out/time_embedder.linear_1,2 — 刻意保留 fp32，正常）
- vae: 2.604B params，**全部 F32**（10.42GB）；audio_vae: 0.151B，全 F32
- key 结构干净：638 keys、50 个 `transformer_blocks.*`、标准 diffusers 命名，
  config 与 `MiniMaxH3Transformer3DModel` 完全匹配 → 排除 key 映射 / 随机初始化
- **疑点**：`model_index.json` 声明了 `transformer_ref/` 子目录，但快照里没有该文件夹；
  下载跨 Aug 25–29 四天。建议与 HF 官方 blob 核对 sha256（沙箱内访问 huggingface.co 被拦）

### Turbo LoRA alpha（直接读 safetensors 头得到，权威）
- `v1.0_768p_4step`: alpha=128　`v1.1_768p_4step`: alpha=128
- **`8step_v1.0_768p`: alpha=8** ← 脚本默认 128 → 强度放大 16 倍（diffusers PR #14408 修的正是这个）
- `v0.1`(544p): metadata 里**没有** alpha

### 06c/06d 与官方验证配方的偏离（嫌疑逐条修订）
1. ~~`low_cpu_mem_usage=True`~~ **撤回嫌疑（2026-09-01 实测）**：diffusers 0.40.0 与
   main 的 `from_pretrained` 都硬性断言「量化加载必须 low_cpu_mem_usage=True」，
   传 False 直接 ValueError（modeling_utils.py:1195）。官方 doc 写 False 与其自身代码
   矛盾（doc bug 或未发布特性），以代码为准。**06c/06d 写 True 是对的**。
2. offload kwargs 缺 `use_stream=True`（官方有；doc 原话 version=2 int8 tensors are
   pinnable）。09b 已带 TypeError 回退：若 0.40.0 不支持会自动降级并打印实际模式。
   **2026-09-01 新证据**：默认 offload（low_cpu_mem_usage=False）会 pin 全部权重，
   transformer 33GB pin 成功后 text_encoder 32GB pin 失败 → CUDA OOM（锁页内存不可
   swap，33+32=65GB > 64GB 物理）。**09b 已改 offload 传 low_cpu_mem_usage=True**
   （不复制不 pin，页可换 swap）——官方配方需要 ~75GB 内存，64GB 机器必须用 True，
   这不是魔改是硬约束。运行时留意打印的 streamed offload ON/OFF。
3. `torch.Generator("cuda:0")`；官方 doc 全用 CPU `torch.Generator()`（三脚本唯一共同点之一）
4. 手工 `add_adapter + load_state_dict` 注入 LoRA，绕开了 PR #14408 的 alpha 修正逻辑

### 已排除（有证据）
- VAE 被 bf16 降精度：`_keep_in_fp32_modules = ["encoder","decoder","quant_conv","post_quant_conv"]`
  强制钉死 fp32，`dtype=bfloat16` 不会下转
- `num_inference_steps` 的 +1：写对了。官方 doc：「counts sigma grid points, the terminal 0
  included」，4 步要传 5

### 关键诊断缺口
从未跑过干净 baseline（bf16 + 50 步 + 无 LoRA + 无 int8 + 最小 canvas）。
06b 是 bf16 但带 LoRA，06c/06d 是 int8 — 三条路都被魔改污染，所以「根因待查」必然卡住。

### 09a 实跑结果（2026-09-01 16:03，用户贴全量输出，我从 mp4 抽帧亲眼确认）
- **VAE 排除嫌疑**：decode[raw]（直接喂 raw latent）近乎完美重建合成图案

### 新首嫌疑：offload 路径与 ComponentsManager 状态机冲突

### 根因（查 modular_pipeline.py 源码 + 官方 doc）
`components_manager` **不是** `from_pretrained`/`update_components` 的 kwarg，

正确传给 pipeline_class）。警告源自 update_components（:2379）——它只认
`self._component_specs` 里的名字，剩余 kwargs 全 ignore。

**更深的坑**：组件注册进 CM 只发生在 `register_components()` 里且满足
`is_from_pretrained`（spec.default_creation_method=="from_pretrained"，源码
:2151/:2187）。**09e/09b 用 update_components 注入"手动 from_pretrained 的实例"
会改成 ComponentSpec(name, type_hint=type) → default_creation_method≠from_pretrained
→ 组件永不注册进 cm** → cm 空 → enable_auto_cpu_offload 管不到任何组件 → 全量
加载 → OOM Killed。**09e 从设计上就是无效对照，勿采信。**

### 官方 doc 实为两条互斥配方（09e 混搭错了）
- **配方 A（80GB 大卡，ComponentsManager + bf16）**：manager=ComponentsManager();
  pipe=ModularPipeline.from_pretrained(...,components_manager=manager);
  pipe.load_components(workflow="t2va",dtype=bf16); manager.enable_auto_cpu_offload(...)
  ——组件由 pipeline 自己按 spec 加载，走 from_pretrained，才会注册进 cm。
- **配方 B（24-32GB 消费卡，int8 + 手动 group offload，官方明确说不用 CM）**：
  pipe=ModularPipeline.from_pretrained(...);  # 不传 cm
  pipe.update_components(transformer=int8实例,text_encoder=int8实例);
  pipe.load_components(...); pipe.transformer.enable_group_offload(...);
  apply_group_offloading(text_encoder...); pipe.vae.to("cuda"); pipe.audio_vae.to("cuda")
  ——**09b 就是配方 B**，官方消费卡唯一路径。故「manual offload 与 CM 冲突」
  首嫌疑**洗清**（消费卡本就不该用 CM）。
