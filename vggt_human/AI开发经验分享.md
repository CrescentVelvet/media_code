# 用 AI 做三维重建开发：五条经验与案例

> 素材来源：media_code 仓（30+ 算法复现目录）与 vggt_human（VGGT-Omega → COLMAP → 3DGS 人像重建流水线）的 README / NOTES / EXPERIMENTS / BACKLOG / AGENTS.md 等文档，以及近两个月的实际协作记录。

---

## 经验一：先把「格式」钉死，再让 AI 批量生产 —— 脚本编号 + README 流程化

**核心观点**：AI 的价值不在单次问答，在于把一次成功的工作流固化成模板。第一个算法由人深度参与、校准格式，之后每复现一个新算法，AI 都自动沿用同一套骨架。

**做法分三步**：

1. **第一个算法人工参与**：让 AI 给出每个脚本的草案，但规定名称以数字开头且语义固定——`00` 配环境、`01` 下模型与数据、`02` 推理/预处理、`04` 训练、`08` 结果搬运（WSL 专用）。把运行流程写进 README：配环境 → 下模型 → 预处理 → 训练 → 结果渲染，每条命令显式写全路径，不许用默认值偷懒。
2. **手动改完再完整跑一遍**：这是最关键的一步。模板里的默认值（conda env 名、路径策略、镜像源、编译选项）都是在这时候校准的；跑不通的地方改成文字规范，而不是记在脑子里。
3. **之后复现任何新算法，把规范喂给 AI 即可**：产出自动同格式，跨会话也不走样。

**案例**：

- media_code 仓的 `AGENTS.md` 就是这份规范：脚本强制数字编号；同一步骤的多个变体用同一数字加字母（`01_pick_and_segment.sh` / `01b_...` / `01c_...`）；跨平台变体也用字母区分（`00_setup_env.sh` 服务器版 / `00a_setup_env.sh` WSL 本机版）；WSL 专用脚本同样编号（`08_move_output.sh`）。
- vggt_human 的 README 把流程固化成 `00 配环境 → 01a 视频抽帧 → 01 人脸增强 → 02 前馈推理 → 03 npz 转 COLMAP → 04 3DGS 训练 → 05 去噪增强 → 06 人脸后处理 → 07 增强训练`，输出目录挂步骤号前缀（`02_vggt/`、`03_source/`、`04_model_3dgs/`），按前缀排序 = 按 pipeline 顺序排序，一眼看出跑到哪一步。
- **效果**：30+ 个算法目录（vggt_human、pdfgs_human、hypir、sam_3d_body、wan22……）共用同一套骨架。换一个新算法，AI 看一遍 AGENTS.md 就能产出风格一致的脚本与文档；新人接手也只看目录结构就知道流程。

**从实施细节再展开几条可照搬的规范**：

- **输出目录挂步骤前缀**：`01_input_face/`、`03b_source_ba/`、`06c_model_3dgs_closeup/`——「谁产生的、哪一步产生的」不用问人。
- **shell 规范细节**：`set -o pipefail`，**不用 `set -e`/`set -u`**（conda activate 会触发未绑定变量静默退出——实测踩出来的）；所有参数 `${VAR:-default}` 可从命令行覆盖；README 铁律：**示例命令必须显式写出全部路径，不靠脚本默认值**。
- **开关默认全开便于消融**：`POSE_ADJUST/POSE_REFINE/ENABLE_DYNAMIC_MASK/ENABLE_MLP_DYNAMIC/USE_DEPTH_NORMAL` 等增强项默认 1，改 0 即是一组 ablation 变量，不需要改代码。
- **可插拔设计**：denoisers.py 用 registry 模式（`DENOISER=diffbir|swinir|none`），一个新模型 = 一个函数 + 一行注册。
- **三文档分工防膨胀**：README 只放运行必须（命令/参数/目录）；原理和排错进 NOTES；实验结论按日期倒序追加进 EXPERIMENTS——否则 README 跑 1k 行后没人找得到命令。
- **配环境脚本要「幂等 + 可重入」**：00 报错后单独重跑 `INSTALL_DEPS=1 bash 00` 就能续上，分段 verify（clone 成功 / import 成功 / nvcc 存在）比「一键长脚本跑到哪算哪」省大量来回。

## 经验二：先文档后代码 —— 把「幻觉」挡在写代码之前

**核心观点**：直接让 AI 上手改代码加功能，最容易出的问题是：跑了几小时对比实验之后，才发现 AI 对某个 API 签名或数据格式的假设是幻觉——时间花了，实验数据还不能用。正确顺序是：**讨论方案 → 确定输入输出规格 → 产出技术文档 → 再写代码**。效率更高，也不容易出错。

**案例**：

- **人脸链路 v2**：八阶段 pipeline（检测 → 匹配 → 重建 → 3DMM 对齐 → 增强 → AvatarGaussian 初始化 → BodyGaussian 初始化 → 训练），先把设计方案与决策记录写成 `DESIGN_face_pipeline.md` 评审产出，再动手实现。
- **方案台账**：`BACKLOG.md` 维护八个候选方案（A~H）的评审记录，每案写明原理、移植难度、验证方法、当前状态——C 案已否决、D 案已实现、B 案优先级最高。动手前先查台账，避免重复实施一个已经否决过的方案，也避免争论已经定过的事。
- **反例（事故换来的纪律）**：没读 `README_wsl.md` 的路径策略章节，就把训练输出目录指向 `/mnt/d`（Windows 盘 drvfs），违反「训练写 Linux 文件系统」规范，性能差还可能触发 9p 文件系统与 git 索引的竞态。事后把「先读规范再动手」写成工作纪律。
- **输入输出规格的威力**：vggt_human 的 NOTES 里写死「VGGT-Omega 的 extrinsic 是 w2c（OpenCV 约定）、intrinsic 是模型预测的实际内参」，03 号转换脚本因此零歧义。反之，如果规格没写清，AI 很容易按 COLMAP 的 c2w 惯例写反坐标——**不报错、不崩溃、结果还「看起来合理」，是最危险的静默失败**。

**「判据先行」是比文档更硬的一层保险**：

- 选型不靠口头争论，用对比表收敛：VGGT-Omega vs Pi3（参数量 / 是否预测真实内参 / w2c 还是 c2w / 点云来源）、原版 3DGS vs PDF-GS（有无 distractor filtering / 是否依赖 gated DINOv3），各一张表，最后落一句结论：「静态场景 → 本目录；有微动 → pdfgs_human」。
- 坐标约定不靠文档猜，用「不合理的数值」反推：Remy 的 `transform_matrix` 按 c2w 解释帧心距锚点 0.8–1.1 m（合理），按 w2c 解释变 7.2 m 且朝向余弦 −0.38（不合理）→ 判定为 c2w；相机前向用夹角余弦 ±0.99 的翻转判定。
- 官方仓 main 分支漂移 = 雪崩源：gaussian-splatting 的 API 签名（Camera / create_from_pcd / training_setup）在不同时点 clone 行为不同，「上周能跑」不是「这周能跑」的证据——要么 pin commit，要么把 API 适配层单独收进 `train_pose.py` 这种 wrapper 里。
- AI 与目标的 Python 版本不一致是隐蔽炸弹：本机 3.13 能过的 f-string 写法（`f"{d["k"]}"`），到 3.10 服务器直接挂在 import，报错行号还有误导性；`ast.parse(feature_version=...)` 查不出来——**终极验证只能拿真实低版本解释器跑一遍**。

## 经验三：换多模态模型，让 AI 直接「看图」debug

**核心观点**：三维重建的 debug 大量依赖渲染图与点云的可视化检查，靠人肉眼在几百张图里找对齐偏差，既耗时又不可复现。换成能直接读图的模型后，把 debug 图贴给 AI，让它自己看、自己归纳偏差，效率是质变。

**案例**：

- **可检视图前置**：流水线的每一步都产出独立可检查的图——02 步出置信度过滤后的彩色点云（scene.ply）、04 步出重建渲染 vs GT 的对比图。这些图本来就是给人看的，现在直接变成给 AI 看的。
- **工作闭环**：贴图 → AI 指出偏差出现在哪些帧、往哪个方向偏 → 回到代码 file:line 定位根因 → 修复后再贴图确认。例如人脸 finetune 的消融实验（A1–A4）和近景注入实验（06e/06g），一次让 AI 读多组对比图归纳差异，比人逐张翻快一个量级。
- **前后对比**：早期用 glm5.3 只能贴日志 + 文字描述现象，AI 隔着一层转述猜问题；换 deepseek v4.1 后直接读图，「描述偏差」这一步从人的活儿变成 AI 的活儿，人只做判断和决策。
- **注意点**：看图也要有数值判据兜底，不能停在「看起来对齐了」。例如视线交汇求目标点的最小二乘，用正规矩阵条件数判断解是否可信（cond 1.9–2.8 才算良态）——残差小但条件数大，说明解在某个方向上没约束，图再好看也不能信。

**「能跑」到「敢信」之间还差验证方法论**：

- 每一步的中间产物都要可检视、可回读：02 出 `scene.ply` 查点云、04 出 renders vs GT、解封装脚本回读 json 直接 diff——**write 进去的值必须能 read 回来比对**。
- 「一次跑通三件事」验证法：cgltf 补丁链路用一次跑批验证 3 个独立断言（buffer 落值？区间等于新值？半径是否内缩？），避免跑三次还归因悬空。
- 结论修正留痕：99c 的 thetaBuffer 问题在 NOTES 里经历了「初始记录 → 09-15 修正 → 后续判读」四轮更新，**错误的旧结论被明确标注「已被取代」但保留历史原貌**，不偷偷改写，容易走回头的路都有路标。
- 可视化自查三坑：同份代码两套像素框约定（`(x,y,w,h)` vs `(x0,y0,x1,y1)`）→ 参数改名 `panel_xywh` 并加 ⚠️ docstring；SVG 多图 id 冲突（单张正常，拼进总览才暴露）→ id 强制带面板后缀；**浅灰标记压在灰点云上「明明画了但看不见」→ 视觉资产也要做对照度校验**。

## 经验四：保密约束下的本机复现 —— 承认差距，收缩战线

**核心观点**：公司保密制度下，服务器上的代码和数据拿不到，本机用 AI 复现注定达不到与服务器一致的效果与速度——环境不同、数据不同、内部工具链缺失。务实的策略是：**不追求全链路等价，把本机收缩成「方案验证台」，专注特定功能模块**。

**案例**：

- **环境差距**：服务器流水线是 COLMAP → 3DGS → HYPIR → SAM3 全家桶；本机只有 WSL2 + RTX 3090 24G + 56GB 内存。本机从 `doll` env 克隆建出 `vggt_human` env，只承担「前馈重建 + 3DGS 训练」这一段的可行性验证。
- **网络是活的**：GitHub、HuggingFace、各镜像站的可达性两周内就会反转（实测 hf-mirror 镜像挂掉、ghfast 加速证书失效、GitHub 直连反而恢复）。教训：每次动手下载前先 curl 复测，不信上周的结论。
- **gated 模型的坑**：VGGT-Omega 权重在 HF 的 gated 仓库，需要申请访问 + HF_TOKEN，蓝区下载链路单独脚本化（`01_download_models.sh`），一次配好处处复用。
- **补偿手段——口径对齐**：服务器侧工具的算法原理（视线交汇最小二乘、±180° 方位角循环补偿等）与本地实现互相印证，本机跑通的模块可以反过来作为服务器方案评审的论据。「本机 ≠ 服务器」不等于「本机没用」，定位成方案论证与功能验证的平台。
- **心态**：接受差距，把目标定为「特定功能跑通 + 产出方案论证材料」，而不是「整条流水线与服务器对齐」。

**蓝区复现的「修路」清单**（先把路修通，再谈跑模型）：

- **代理与凭证集中管理**：所有项目共用一个 `proxy.env`（代理 + `HF_TOKEN` + `HF_ENDPOINT` 镜像），`_env.sh` 统一 source 并 export CA bundle（集团代理 TLS 拦截需要）；**仓级 gitignore，凭证绝不入库**。
- **镜像与 Fallback 是常态而不是意外**：`gitlab.inria.fr` 被墙 → 00 脚本自动 fallback 到 GitHub 镜像（simple-knn）；PyPI 慢 → tuna 镜像；HF 连不上 → 换可用镜像。
- **conda env 与 CUDA 编译三板斧**：CUDA 扩展编译失败的三个根因——gcc 太老（`conda install gxx_linux-64=12`）、`CUDA_HOME` 指错版本（torch cu118 vs 系统 cuda-12.x）、GLM 头文件缺失。00 脚本自动检测 CUDA 与 torch 匹配，**不是「装到能跑」，而是「自动选对版本」**。
- **WSL 专属坑单列文档**：drvfs(`/mnt/d`）上编译慢 5–10 倍且 symlink 会坏，训练/编译只在 Linux fs 做，跑完用编号脚本（08）搬到 Windows 盘。
- **CRLF 在行尾会炸跨平台链路**：Windows 编辑过的 .sh 在 WSL 报 `syntax error near unexpected token '('`，靠仓级 `.gitattributes` 强制 LF 在源头解决，不是罗列排错条目。

## 经验五：同事用得少，应该怎么介绍

给没怎么用过 AI 的同事讲，不要讲「AI 有多强」，要讲「我踩过什么坑、省下了什么时间」。建议按上手成本从低到高分层介绍：

| 层次 | 做什么 | 门槛 |
|---|---|---|
| 1. 问根因 | 粘贴完整日志，要「根因分析 + 具体 file:line」，而不是问「这个报错怎么办」 | 零门槛，当天见效 |
| 2. 文档型任务 | 让 AI 整理实验记录、写 README 初稿、把踩坑写成排错手册（我们的 NOTES.md 里 70% 的条目来自真实报错） | 低 |
| 3. 规范型任务 | 把团队约定写成 AGENTS.md 这类「给 AI 看的规范」，AI 就能跨会话复刻风格——这是「一个人 + AI 稳定产出」的关键 | 中 |
| 4. 方案三段式 | 讨论方案 → 技术文档 → 代码；debug 时贴图让 AI 读 | 中 |
| 5. 诚实性底线 | 不确定的结论让 AI 标【存疑】，数字必须能回原文核对——读起来很顺但没依据的结论，比没有结论更危险 | 意识层面 |

**给同事演示时的三个现成故事**：

- **误删目录事故**：不读 AGENTS.md 目录规范就 git rm，触发 WSL 9p 与 git 索引竞态，整个 vggt_human 被识别为删除——「AI 每次工作前先读规范，不凭印象」这条纪律是事故换来的。
- **三跳之外的报错**：astcenc 缺执行位，表象是 PIL 报 FileNotFoundError，真因是子进程错误被重定向进 `/dev/shm` 临时目录、进程退出即删。教训：**凡是把 stderr 重定向进临时目录的子进程，上游必须前置检查**。
- **静默失败的 w2c 误读**：坐标写反不报错、不崩、残差只差一点，但结果全错——演示「为什么必须给 AI 数值判据，不能只看跑没跑通」。

**一个反直觉的总结**：用 AI 的第一生产力不是省下的写代码时间，而是**每一次排错都被迫沉淀成文档**。团队里文档厚的地方，AI 越好用；这就是「越用越值钱」的复利。README/NOTES 里 70% 的「可能遇到的问题」都来自真实报错——**把排错过程直接写进文档并标注日期**，文档才能从「原理手册」长成「团队查证手册」。

## 附：配套的工作流纪律（团队约定）

- **commit 约束**：`<项目名>: <简短描述>`，一行标题 + 至多 1–2 行正文；**AI 不得 push**，远端始终保持「人确认过的干净快照」作为最后救回手段。
- **工作流：「继续」+ checkpoint commit**：每步完成后立刻 commit 并汇报（✅/⚠️ 状态 + 表格），debug 靠检视 debug 图像 → 根因 → commit 推进。
- **诚实性约束内置**：不确定就标注 `【存疑】/【推测】/【待核实】`；数字、引文、代码路径必须能回原文（file:line）核对。
