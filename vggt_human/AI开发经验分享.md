# 用 AI 做三维重建开发：五条经验与案例

**背景**：本文来自 media_code 仓（30+ 个算法复现目录，含 vggt_human 三维重建流水线）近两个月的实际协作记录。文中所有数字、路径、错误信息均可在仓库文档中回查，来源见文末「可核对来源」一节。写作目的是把可复用的做法留下，不讨论模型能力本身。

---

## 经验一：先固定脚本编号与目录规范，再让 AI 批量产出

### 1.1 做法：第一个算法人工校准，之后靠规范复用

流程分三步：

1. **第一个算法让 AI 出草案，人来定格式**。要求每个脚本名称以数字开头且语义固定：`00` 配环境、`01` 数据准备、`02` 推理、`03` 格式转换、`04` 训练、`08` 结果搬运。同时把执行顺序写进 README：配环境 → 下模型 → 预处理 → 训练 → 结果渲染。
2. **手动改完再完整跑一遍**。模板里的默认值（conda env 名、路径、镜像源、编译选项、迭代数）都是在这一步校准的。跑不通的地方改成文字规范写进 `AGENTS.md`，而不是留在对话记录里。
3. **之后复现新算法时，把 `AGENTS.md` 直接交给 AI**，产出的目录结构与脚本风格自动一致，不需要每次重新说明。

### 1.2 已成文的规范条文

**编号规则**（`media_code/AGENTS.md`）：

- 同一步骤的多个变体用同一数字加字母：`01_pick_and_segment.sh` / `01b_...` / `01c_...`。
- 跨平台变体同样用字母区分：`00_setup_env.sh`（服务器）/ `00a_setup_env.sh`（WSL 本机）。
- 不写无编号的 `run_xxx.sh`、`stop_xxx.sh` 这类 wrapper；一键脚本也要编号（`04_run.sh`、`05_stop.sh`）。
- 收尾类脚本单独占一个数字段：vggt_human 的 `99a`（收集 ply）～ `99j`（图面渲染）共 10 个，各自职责单一。

**参数注入方式**：所有环境变量用 `${VAR:-default}` 形式，允许命令行覆盖全部路径。README 里有一条硬性要求——示例命令必须显式写出模型路径、输入路径、输出路径，不能用 `...` 占位。这条要求的作用是：复制命令即可复现，不需要回读脚本源码找默认值。

**shell 约定**（`AGENTS.md` 第 3 节）：用 `set -o pipefail`，不使用 `set -e` 和 `set -u`。原因有实测依据：`conda activate` 会触发未绑定变量，在 `set -u` 下导致脚本静默退出，且不打印任何报错；`set -e` 会让中间步骤的错误在无输出的情况下终止流程。

**输出目录命名**：`$RESULTS_DIR/` 下每个产物带产生它的步骤号前缀。vggt_human 的实际前缀表：

| 前缀 | 产生步骤 | 产物 |
|---|---|---|
| `01a_` | 视频抽帧 | `01a_input_frames/` |
| `01_` | 前处理人脸增强 | `01_input_face/` |
| `02_` | VGGT-Omega 前馈推理 | `02_vggt/<scene>/` |
| `03_` | npz → COLMAP | `03_source/` |
| `03b_` | COLMAP BA 精修 | `03b_source_ba/` |
| `04_` / `04b_` | 3DGS 训练 | `04_model_3dgs/` / `04b_model_3dgs_ba/` |
| `05_` | 渲染新视角 + 去噪 + AdaIN | `05_novel_*`、`05_source_aug/` |
| `06_`～`06g_` | 人脸增强与近景注入各变体 | `06_source_aug_face/`、`06c_merged_face_images/` 等 |
| `07_` | 增强场景训练 | `07_model_3dgs_denoise/` |

作用：按前缀排序即等于按执行顺序排序，看目录就能判断当前跑到哪一步、每个产物的上游是谁。

**开关设计利于消融**：训练脚本的增强项默认全开，改 0 即关闭，不需要改代码——`POSE_ADJUST`、`POSE_REFINE`、`ENABLE_DYNAMIC_MASK`、`ENABLE_DYNAMIC_FILTER`、`ENABLE_MLP_DYNAMIC`、`USE_DEPTH_NORMAL`。一组消融实验就是六行环境变量。

**可插拔模块**：去噪模型用注册表模式（`denoisers.py` 的 `DENOISERS` 字典），`DENOISER=diffbir|swinir|nafnet|none`。接入新模型 = 写一个函数 + 注册一行。

**文档三分工**：README 只放运行必需内容（命令、参数表、目录布局、简短说明）；原理与排错进 NOTES；实验结论按日期倒序追加进 EXPERIMENTS。这条分工是被文档膨胀逼出来的——vggt_human 的 README 一度把排错条目全部塞在同文件内，运行信息被淹没；后来 12 条排错整体迁入 NOTES，README 里只留一行指路。

### 1.3 效果与边界

30+ 个算法目录（vggt_human、pdfgs_human、hypir、sam_3d_body、wan22、minimax_h3 等）共用同一套骨架。新算法接入时，AI 只需读一遍 `AGENTS.md` 即可产出同编号、同参数风格、同文档结构的脚本；对人而言，脚本编号本身就是执行顺序说明。

需要说明的是，这套格式的作用是让协作与排查成本可控，不直接提升算法效果。它约束的是产出物的组织方式，而这一层最适合交给 AI 批量执行——因为格式是确定的，不需要判断力。

## 经验二：先确定方案与接口规格，再让 AI 写代码

### 2.1 问题：接口假设错误会浪费整轮实验

直接让 AI 改代码加功能，最常见的失败模式是：AI 对某个 API 签名或数据格式的判断有误，代码能跑、实验能出数，但对比跑了几小时后发现前提不成立，整轮数据作废。这类错误不会在运行时报错，只在结果解读时暴露。

### 2.2 做法：方案文档 + 输入输出规格，通过后再写代码

顺序固定为：讨论方案 → 确定输入输出规格 → 产出技术文档 → 编码。技术文档要写明三件事：数据从哪来（具体文件与字段）、中间表示是什么形态（张量形状 / 坐标系 / 单位）、产物写到哪（路径与格式）。

### 2.3 案例

**设计文档先行**：人脸链路 v2 是八阶段流水线（检测 → 匹配 → 重建 → 3DMM 对齐 → 增强 → AvatarGaussian 初始化 → BodyGaussian 初始化 → 训练），先产出 `DESIGN_face_pipeline.md`（含 FLAME + DECA + 468 点 + 重心绑定 + 表情驱动的方案与决策记录），评审通过后才开始实现。

**方案台账**：`deformable_human/BACKLOG.md` 维护八个候选方案（A~H）的评审记录，每案写明原理、移植路径、验证方法、当前状态。实际价值在状态标注——C 案已否决、D 案已实现、B 案优先级最高。动手前查一次台账，避免重复实施已否决方案，也避免重复讨论已定结论。

**输入格式规范**：Remy 采集包（华为手机 3D 采集）被定为标准输入格式后，其结构（`transforms.json` + `image/*.heic` + `pcd.ply`）与位姿转换约定（`w2c = inv(M @ diag(1,-1,-1,1))`）写进 `som_human/README.md` 的「输入数据格式」节。规范写清后，后续所有脚本对输入的理解一致。

**规格缺失的代价（反例）**：把训练输出目录指向 `/mnt/d`（Windows 盘 drvfs 挂载），违反 `README_wsl.md` 的路径策略（训练写 Linux 文件系统）。drvfs 上编译慢 5–10 倍，且 WSL 的 9p 文件系统与 git 索引存在竞态。事后把「操作前先读对应 README 章节」写成工作纪律。

### 2.4 用数值判据替代文档猜测

规格文档解决「约定是什么」，数值判据解决「约定到底对不对」。以下四个判定来自 Remy `transforms.json` 的实测，均不依赖文档说明：

| 待定问题 | 判据与实测值 | 结论 |
|---|---|---|
| `transform_matrix` 是 c2w 还是 w2c | 按 c2w 解释，各帧光心到 `anchor_point` 水平距离恒为 0.81–1.08 m（等距环绕）；按 w2c 解释（C = −Rᵀt）变成 7.2 m，朝向角余弦仅 −0.38 | c2w |
| 相机前向是 +Z 还是 −Z | 取 look = −R[:,2] 与 (anchor − C) 的夹角余弦均值 0.9926；按 +Z 则为 −0.9926（等于所有相机背对目标） | −Z（OpenGL 约定） |
| 世界系是否 Z-up | 相机 +Y 轴在世界 Y 的分量均值 0.889（min 0.805 / max 0.984） | +Y 向上 |
| 是否还要跑 COLMAP SfM | 位姿来自 AR Engine VIO，自带米制尺度；同 json 内 155 帧内参唯一组合数为 1（单一标定而非逐帧估计） | 不跑，会引入重投影误差并丢尺度 |

**选型对比用表格收敛**：VGGT-Omega vs Pi3（参数量 1B vs ~300M、是否预测真实内参、w2c 是否可直接使用、点云来自深度反投影还是模型直接输出）；原版 3DGS vs PDF-GS（有无 distractor filtering、是否依赖 gated DINOv3、30k 单 phase 还是 4×10k）。结论落到一句可执行判断：「静态场景用本目录，有微动（呼吸、头发飘动）用 pdfgs_human」。

**官方仓 API 漂移的实测记录**（NOTES 排错 6b）：gaussian-splatting main 分支更新过 API 签名——`Camera.__init__` 增加 `resolution/depth_params/invdepthmap/uid`，`create_from_pcd` 增加 `cam_infos`，`training_setup` 要求完整 config 对象，`densify_and_prune` 增加 `max_screen_size/radii`。「上周能跑」不构成「这周能跑」的证据。对策二选一：pin commit，或把适配层收敛进 `train_pose.py` 这类 wrapper。

**语言版本陷阱**（NOTES 2026-09-23，逐条在 3.10.20 上实测）：本机 Python 3.13 通过、服务器 3.10 报 SyntaxError 的写法：

| 写法 | 3.10 结果 |
|---|---|
| `f"{d["k"]}"`（外层双引号 + 内层同类引号） | SyntaxError: f-string: unmatched '[' |
| 表达式段里出现反斜杠（`f"{s.replace('\n','')}"`） | SyntaxError |
| `f'''{d["k"]}'''`（三引号外层） | 合法 |
| `f"{d['k']}"`（内外引号类型不同） | 合法 |

`ast.parse(src, feature_version=(3,10))` 查不出这一类——PEG 解析器不再按旧规则限制 f-string，三种 feature_version 实测全部通过。可靠的验证是用真 3.10 解释器跑一遍；日常自查用 `99h_check_py_syntax.py`（基于 tokenize，需 Python ≥ 3.12 运行）。

## 经验三：让模型直接读渲染图做 debug（实际收益与边界）

### 3.1 前提：每一步都产出可检视图

流水线每步都有独立可检查的产物：02 步出置信度过滤后的彩色点云 `scene.ply`、04 步出重建渲染与 GT 的成对图、05 步出去噪前后对照与 alpha 覆盖率图、99g 出相机轨迹与视角约束图。这些图原本是给人看的，模型可读图后，同时成为给 AI 的输入。

### 3.2 收益：从「文字转述」变成「模型自己看」

实测时间点（2026-09-28 记录）：从该日起模型可直接读 PNG 做诊断，不再依赖像素统计或 ASCII 色相图这类间接手段。工作闭环变为：贴图 → 模型指出偏差出现在哪些帧、朝哪个方向偏 → 回到代码 file:line 定位 → 修复后再贴图确认。

对比：使用 glm5.3 时只能贴日志 + 文字描述现象，模型隔一层转述推测；换 deepseek v4.1 后读图这一步由模型承担，人只做判断与决策。

### 3.3 具体案例

**近景注入的归因实验（06e/06g，2026-09-04）**：对照两组同等训练量（20k 步 @ lr_scale=0.2）：

- 06f（纯续训无注入）：近景 LPIPS 持平（0.3048→0.3049），锐度 +3~6%（噪声级）。
- 06e（新增近景作为完整训练视角注入，222 views）：近景 LPIPS 全降（p00 0.305→0.260、p03 0.202→0.137），锐度 +28%~+324%，训练视角人脸区 Laplacian +45% 且 LPIPS 不升。
- 06g（round2 再注入）：近景 LPIPS 再降 10~23%，锐度再涨 +22~71%，PSNR +1.2~1.5 dB；两轮未饱和但增益递减（round1 训练视角 +45% vs round2 +17%）。

这类对比涉及几十帧渲染图，逐张人工翻看效率低；让模型一次读多组图归纳差异，是这一步提速的主要来源。

**人脸 finetune 消融的反直觉结论（2026-09-04）**：对照实验（同等训练量，唯一差异 face_weight 0 vs 1.0）显示，人脸监督（masked-L1 → HYPIR 增强图）对人脸区锐度无可测量贡献（+4.04% vs +3.98%，逐帧差在噪声内）。此前 v1~v6 观察到的提升，实际来自「30k 基线欠收敛 + 更高 lr 继续训练」。后续确认：face_weight 1.0→2.0 结果逐像素持平（瓶颈是 lr_scale 不是权重）；lr_scale 0.1→0.2 把增益从 +2.0% 提到 +2.7%/10k 步。

**损失项方向冲突的定量定位（SSIM composite 修正，2026-09-05）**：masked-L1 路径里 L1 在人脸区推向增强图，SSIM 项却全画幅对着原图计算，两项在人脸区内更新方向接近正交。用合成测试测「更新方向」与「补细节方向」的余弦：

| 项 | 余弦 |
|---|---|
| L1 人脸项 | +0.81 |
| SSIM 旧（对原图） | +0.18 |
| SSIM 新（composite） | +0.94 |
| 总 loss 旧 → 新 | +0.57 → +0.95 |

即 λ_dssim=0.2 的 SSIM 项把总方向从 0.81 稀释到 0.57（是正交稀释，不是反向），masked-L1 的效果被吃掉大半。修法是人脸区内 SSIM 比对目标换成同一张 composite，区外仍为原图。

### 3.4 边界：图看对不等于结论对，数值判据不能省

模型看图能发现「哪里不对」，但判断「是否可信」仍需数值。三个实测例子：

- **最小二乘解的可信性**：视线交汇求目标点的最小二乘，正规矩阵条件数 cond 1.9–2.8 才算良态。残差小但条件数大，说明解在某个方向上无约束，图面看起来正常也不能采信。
- **球心取点的对比**（99g，10 个样本）：`anchor_point` 直接取用 vs 最小二乘视线汇聚中心——垂距 RMS 0.081 m vs 0.205 m，视线夹角 3.46° vs 9.54°，10:0。数值差异明确，图面看不出这个量级区别。
- **拍脑袋常数被实测否掉**：原移植代码用 `0.9×avg / 1.2×avg` 定半径区间，而实测 `view_limits.json` 是 R[0.432, 2.159]、init 半径 1.909，按固定比例只会给 [1.72, 2.29]，量级都不对；另外 `vulkan_to_webgl` / `webgl_to_vulkan` 是同一个函数 `[x,−y,−z]` 且对 camera 与 target 同时施加（刚体变换，角度结果不变），属死代码。

### 3.5 配套工具链细节

读图 debug 依赖截图能力，这条链路上有几个实测结论：

- **Edge headless 截图**：`--headless --screenshot=` 在 Edge 154 起 100% 失效（进程 exit 0、无 stderr、无文件输出；`--dump-dom` 同样无输出；`--no-sandbox`、版本目录 exe、PowerShell `Start-Process` 均无效）。此前记录的「约 1/3 概率静默不产出」是误判，实质是 `--user-data-dir` 复用导致确定性失败。可行路径是启动 headless 实例后走 CDP `Page.captureScreenshot`，已封装为 `99i_render_report_figs.js`（自探测 Edge 版本目录 → spawn `--remote-debugging-port` → `PUT /json/new` 开 tab → `Emulation.setDeviceMetricsOverride(deviceScaleFactor=3)` → 截图）。附带一个坑：`child.kill()` 后需 sleep 500 ms 再删 profile 目录，否则 Crashpad 句柄未释放报 EBUSY。
- **图面可读性有量化判据**：4 张汇报图原为 1180 px 宽画布 + 11–14.5 px 字号，字号/宽度比 0.93%；PPT 16:9 满宽（约 30 cm）插入时最小字号折合约 7.9 pt，投影必糊。目标比值 ≥1.5%（等效 ≥14 pt）。最终画布收窄到 880 px、字号重排（正文 12→14、说明 11→13、卡标题 13→17），PNG 输出 2640 px 宽（880×3）。

## 经验四：保密限制下，把本机定位为「特定功能验证环境」

### 4.1 差距是客观的，先列清楚

服务器上的代码与数据不可取出，因此本机复现**不可能**达到与服务器一致的效果与速度。本机条件：WSL2 + RTX 3090 24 GB，内存 56 GB + swap 128 GB，CPU i9-12900K 8 核；服务器侧是 COLMAP → 3DGS → HYPIR → SAM3 的完整链路，另有一套 3DGS 相机位姿调整工具（本机没有）。

### 4.2 做法：不追求全链路等价，只做单功能验证

- **env 独立建、独立命名**：本机从 `doll` env 克隆出 `vggt_human` env（继承 torch ≥2.3 与 3DGS CUDA 扩展），另建 `colmap` env（conda-forge colmap 4.2.1 cuda_129，GPU SIFT 可用）。新任务优先新建独立 env，不污染已有环境。
- **路径策略落到脚本**：训练/编译写 Linux 文件系统（`~/output/`、`~/repos/`），跑完用编号脚本 `08_move_output.sh` 搬到 Windows 盘；脚本内所有路径都用 `${VAR:-default}` 允许覆盖，本机与服务器共用同一份脚本。
- **环境问题记录成文档**：conda 不在 PATH 时的 fallback、CUDA 扩展编译的三个根因（gcc 版本、`CUDA_HOME` 指向、GLM 头文件）、镜像源配置，全部写进 `NOTES.md` 排错条目与 `README_wsl.md`。

### 4.3 实测的具体困难

**网络可达性会漂移**：2026-09-21 与 2026-10-11 两次复测结论相反——`hf-mirror.com` 直连超时（镜像失效）、`ghfast.top` SSL 自签名证书失效、`github.com` 反而恢复直连可 clone、`raw.githubusercontent.com` 仍挂起。对策是动手前 curl 复测，并把当日结论写进 memory log 标注日期，而不是当作长期事实沿用。

**gated 权重**：VGGT-Omega 在 HF 是 gated 仓库，需要申请访问 + `HF_TOKEN`，下载走单独的 `01_download_models.sh`（4.6 GB，镜像正常时约 3 分钟）。

**编译性能**：仓库在 `/mnt/c/`、`/mnt/d/`（drvfs）上编译比 Linux 文件系统慢 5–10 倍，且 symlink 可能损坏；vhdx 删除文件后不自动收缩，需 `wsl --shutdown` + `diskpart` → `select vdisk file=...` → `compact vdisk`。

**环境隔离细节**：colmap 4.2.1 的 conda-forge 配方漏声明 `openimageio`，必须补钉 `openimageio=3.1`（ABI 锁 3.1，装 3.2 会缺 `libOpenImageIO.so.3.1`）；不要用 tuna 的 conda 通道（repodata 404/落后导致 solver 卡死）；COLMAP 4.x 的 mapper 要求 `--output_path` 目录已存在（3.x 会自动建）。

### 4.4 补偿手段：用同族实现做口径对照

服务器侧工具拿不到，但本机有同族能力的脚本，可以互相印证并作为评审论据：

| 服务器工具模块 | 本机同族实现 | 对照口径 |
|---|---|---|
| `crop_camera_by_angle.py`（视线交汇最小二乘 + 方位角循环补偿） | `99g_plot_capture_trajectory.py`（逐帧增量解缠、球壳扇块区间） | 角度区间定义一致：az / el / r 三区间 + 显式余量 |
| `generate_camera_files.py`（生成三件套 json） | `99c_repack_view_limits.py`（Phi/Theta/Radius 换算） | 字段换算约定以 99c 为准，三轴落地字段可逐项对照 |
| 编码与封装 | `99b` 正向四步 | 正向流程步骤一一对应 |
| MP4 解封装标签页（反向入口） | `99e` 反向三步 | 反向解出的 json 可直接与原始值 diff |

在工作记录里，这类对照被明确标注为「同族脚本本机实测」，不冒充服务器工具的数据。这是本机环境在保密约束下仍然具备价值的核心用法：**做不了等价复现，但能为服务器侧方案提供可核对的数值论据与格式约定**。

## 经验五：典型踩坑案例整理与检查清单

以下案例按「现象 → 定位过程 → 根因 → 沉淀的规则」整理，均为实际发生过的问题。

### 案例 1：静默失败——坐标约定反了但结果「看起来合理」

- **现象**：位姿数据按 w2c 解释后，流程不报错、不崩溃，渲染结果肉眼看着也正常。
- **定位**：用地心距做判据——按 w2c 解释（C = −Rᵀt）帧心距变成 7.2 m、朝向余弦 −0.38；按 c2w 解释则恒为 0.81–1.08 m、朝向余弦 0.9926。
- **根因**：约定判断错误，但错误只体现在数值量级上，不影响流程继续执行。
- **规则**：对每个外部数据格式，先找一条能区分正确/错误解释的数值判据（距离、夹角余弦、条件数），再写代码。不报错不等于正确。

### 案例 2：三跳之外的报错——子进程 stderr 被重定向进临时目录

- **现象**：PIL 报 `FileNotFoundError`，指向一个本该存在的中间文件。
- **定位**：往前追三层调用发现，真正的原因是 `astcenc` 可执行文件缺少执行位，子进程启动失败；而该子进程的 stderr 被重定向进 `/dev/shm` 下的临时目录，进程退出即删，错误信息从未浮出。
- **根因**：错误被重定向吞掉，表象与真因相隔三跳。
- **规则**：凡把 stderr 重定向进临时目录的子进程，上游必须做前置检查（`99e` 已加启动时权限扫描）；排查时补一层执行前检查，而不是只改表象。

### 案例 3：跨平台文件系统与 git 索引竞态

- **现象**：一次 `git rm` 后整个 `vggt_human` 目录被 git 识别为全部删除。
- **定位**：操作发生在 WSL 的 9p 挂载路径上，文件系统与 git 索引更新不同步。
- **根因**：未先读 `AGENTS.md` 的目录规范就执行删除操作，叠加 9p 与 git 的竞态。
- **规则**：涉及批量删除、目录结构调整的操作前，先读对应规范章节；在 WSL 挂载路径上避免这类操作（本次用 `git restore` 恢复成功）。

### 案例 4：「看起来执行了」——工具静默未产出

两个同源案例：

- **批量删除被静默取消**：授权确认弹窗超时，操作被取消，但没有任何报错、文件一个没删，看上去像已完成。规则：长任务收尾涉及批量删除或工作区外写入时，要在回复里显式标注「等授权」，不能默认已执行；动手前先核对目标目录实际状态。
- **截图工具静默不产出**：`--headless --screenshot=` 进程 exit 0、无 stderr、无文件。规则：批处理脚本必须校验产出文件存在且非空，而不是只看退出码。

### 案例 5：渲染层看不见的错误（SVG / CSS）

三个案例都属于「XML 解析与标签配平全部通过，只有截图能看见」：

| 现象 | 根因 | 规避方式 |
|---|---|---|
| 彩色标注全部变灰（83 个标签受影响） | presentation attribute（`fill=`）优先级低于 CSS 类选择器，`<text class="f-s" fill="#059669">` 被类里的 `fill:#6B7280` 覆盖 | 改用行内 `style="fill:#..."`（优先级最高） |
| 线条渲染成粗黑条 | `class="ln-data"` 引用了样式表里不存在的类名，元素回落到 SVG 默认 `fill:black` / `stroke:none` | 新增语义类后立刻用 `grep` 与 CSS 定义对表；校验脚本用 used − defined 差集拦截 |
| 拼成总览后第 2~6 张图被第一张的裁剪框裁掉 | 多图内联进同一文档时 `clipPath` 的 id 重复，`url(#id)` 只解析到第一个 | id 强制带面板后缀 |

补充一个同类的约定冲突：同一份代码里两套像素框约定并存——`clip_rect(panel)` 与 `_fit_view(panel)` 的参数是 `(x, y, w, h)`，而 `View(...)` 的后四个参数是 `(x0, y0, x1, y1)`。接错不报错，只会画出比例尺错误的图。规避：参数改名 `panel_xywh` 并在 docstring 标注。

### 案例 6：本机工具链的编码与语法问题

- **Python 3.13 通过、3.10 挂**：见经验二 2.4 的 f-string 表。规则：改完 `.py` 用真 3.10 解释器 `py_compile` 复验。
- **PowerShell 5.1 捕获 git 输出按 cp936 解码**：中文 commit message 回读显示乱码，但 `git cat-file commit HEAD` 确认仓库内是正确 UTF-8。规则：乱码只在捕获层，不要据此重做 commit；读取前先设 `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`。
- **不要用 PowerShell 读改写源码**：`Get-Content -Raw` + `Set-Content -Encoding UTF8` 一次替换就会把 UTF-8 中文按 ANSI 读取，造成不可逆乱码。规则：改源码一律用编辑器工具或 Python 的 `read_bytes` / `write_bytes`。

### 案例 7：实验对比本身的陷阱

- **A/B 对比的随机性对齐**：`vae.encode().latent_dist.sample()` 每次前向都从固定 seed 的随机流取新样本，输出对「第几次调用」敏感（相邻两次前向 mean|Δ|≈0.011）。对比提速前后必须对齐调用序号，否则量到的是假差异；同序号下逐位可复现（两次独立运行 mean|Δ| = 0.000/255）。最终实测：base 170 ms/张 → +cache_text 161 → +merge_lora 139 → +compile 130。
- **torch.compile 的 cache_size_limit 陷阱**：diffusers 的 `Attention.forward` 里有 `inspect.signature(self.processor.__call__)`，dynamo 对每个 attention block 的 processor 对象 id 加 guard，UNet 十几个 block 各需一份编译；默认 `cache_size_limit=8` 撑爆后 dynamo 放弃编译并退回 eager，但保留 dynamo 开销，实测 175 ms 变成 1687 ms（慢 10 倍）。修法：compile 前把 `torch._dynamo.config.cache_size_limit` 抬到 64。另外 compile 收益需按批量门控——增量约 12 ms/张，一次性编译约 28 s，约 2300 张才回本，小批量编译是净亏。
- **渲染基线的量化对照**：早期 `train_pose.py` 渲染平均亮度 0.8（全黑 + 白点）而 GT 为 127.9，比值 0.006，PLY 只有 17,912 个高斯；官方 30000 iter 后亮度 127.6（比值 0.998），PLY 290 MB。有这组数字，「渲染是不是黑的」不靠目测。

### 检查清单（可直接复用）

| 场景 | 检查项 |
|---|---|
| 接入新的外部数据格式 | 是否找到一条能区分正确/错误解释的数值判据（距离、夹角余弦、条件数） |
| 修改训练/推理代码前 | 输入输出规格是否写明（形状、坐标系、单位、路径）；官方仓 API 是否 pin 或用适配层 |

| 写 `.py` 之前/之后 | 目标解释器版本是否确认；是否用低版本解释器复验过语法 |
| 批量删除 / 工作区外写入 | 目标目录实际状态是否核对过；是否需要显式说明「等授权」 |
| 图面产物 | 是否有数值判据兜底；字号/画布比是否达标；类名与 id 是否做过一致性校验 |

## 附：与 AI 协作的工作流纪律（团队约定）

- **commit 格式**：`<项目名>: <简短描述>`，一行标题 + 至多 1–2 行正文；AI 不得 push，远端始终保持「人确认过的干净快照」，作为本地出错时的恢复基线。
- **推进方式**：逐步推进，每步完成后立即 commit 并汇报（状态 + 表格），再进入下一步；这样每步可回滚，阶段成果可追溯。
- **不确定性的标注**：不确定的结论标注 `【存疑】/【推测】/【待核实】`；数字、引文、代码路径必须能回原文（file:line）核对。带标注的诚实报告优于通顺但无依据的结论。
- **排错的信息量**：提供完整日志与复现命令，要求根因定位到具体 file:line，而不是表层修补。
- **文档的沉淀位置**：排错过程写进 NOTES 并标注日期；实验结论按日期倒序追加进 EXPERIMENTS；跨会话有效的约定写进 memory log。vggt_human 的 NOTES 中约 70% 的排错条目来自真实报错，这些条目构成后续同类问题的第一手参考。
