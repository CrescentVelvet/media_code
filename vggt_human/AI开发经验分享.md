# 用 AI 做三维重建开发：五条经验与案例

> 素材来源：media_code 仓（30+ 算法复现目录）与 vggt_human（VGGT-Omega → COLMAP → 3DGS 人像重建流水线）的 README / NOTES / EXPERIMENTS / BACKLOG 等文档，以及近两个月的实际协作记录。

---

## 经验一：先把「格式」钉死，再让 AI 批量生产 —— 脚本编号 + README 流程化

**核心观点**：AI 的价值不在单次问答，在于把一次成功的工作流固化成模板。第一个算法由人深度参与、校准格式，之后每复现一个新算法，AI 都自动沿用同一套骨架。

**做法分三步**：

1. **第一个算法人工参与**：让 AI 给出每个脚本的草案，但规定名称以数字开头且语义固定——`00` 配环境、`01` 下模型与数据、`02` 推理/预处理、`04` 训练、`08` 结果搬运（WSL 专用）。把运行流程写进 README：配环境 → 下模型 → 预处理 → 训练 → 结果渲染，每条命令显式写全路径，不许用默认值偷懒。
2. **手动改完再完整跑一遍**：这是最关键的一步。模板里的默认值（conda env 名、路径策略、镜像源、编译选项）都是在这时候校准的；跑不通的地方改成文字规范，而不是记在脑子里。
3. **之后复现任何新算法，把规范喂给 AI 即可**：产出自动同格式，跨会话也不走样。

**案例**：

- media_code 仓的 `AGENTS.md` 就是这份规范：脚本强制数字编号；同一步骤的多个变体用同一数字加字母（`01_pick_and_segment.sh` / `01b_...` / `01c_...`）；跨平台变体也用字母区分（`00_setup_env.sh` 服务器版 / `00a_setup_env.sh` WSL 本机版）；WSL 专用脚本同样编号（`08_move_output.sh`）。
- vggt_human 的 README 把流程固化成 `00 配环境 → 01a 视频抽帧 → 01 人脸增强 → 02 前馈推理 → 03 npz 转 COLMAP → 04 3DGS 训练 → 05 去噪增强 → 06 人脸后处理 → 07 增强训练`，输出目录挂步骤号前缀（`02_vggt/`、`03_source/`、`04_model_3dgs/`），按前缀排序 = 按 pipeline 顺序排序，一眼看出跑到哪一步。
- **效果**：30+ 个算法目录（vggt_human、pdfgs_human、hypir、sam_3d_body、wan22……）共用同一套骨架。换一个新算法，AI 看一遍 AGENTS.md 就能产出风格一致的脚本与文档；新人接手也只看目录结构就知道流程。

## 经验二：先文档后代码 —— 把「幻觉」挡在写代码之前

**核心观点**：直接让 AI 上手改代码加功能，最容易出的问题是：跑了几小时对比实验之后，才发现 AI 对某个 API 签名或数据格式的假设是幻觉——时间花了，实验数据还不能用。正确顺序是：**讨论方案 → 确定输入输出规格 → 产出技术文档 → 再写代码**。效率更高，也不容易出错。

**案例**：

- **人脸链路 v2**：八阶段 pipeline（检测 → 匹配 → 重建 → 3DMM 对齐 → 增强 → AvatarGaussian 初始化 → BodyGaussian 初始化 → 训练），先把设计方案与决策记录写成 `DESIGN_face_pipeline.md` 评审产出，再动手实现。
- **方案台账**：`BACKLOG.md` 维护八个候选方案（A~H）的评审记录，每案写明原理、移植难度、验证方法、当前状态——C 案已否决、D 案已实现、B 案优先级最高。动手前先查台账，避免重复实施一个已经否决过的方案，也避免争论已经定过的事。
- **反例（事故换来的纪律）**：没读 `README_wsl.md` 的路径策略章节，就把训练输出目录指向 `/mnt/d`（Windows 盘 drvfs），违反「训练写 Linux 文件系统」规范，性能差还可能触发 9p 文件系统与 git 索引的竞态。事后把「先读规范再动手」写成工作纪律。
- **输入输出规格的威力**：vggt_human 的 NOTES 里写死「VGGT-Omega 的 extrinsic 是 w2c（OpenCV 约定）、intrinsic 是模型预测的实际内参」，03 号转换脚本因此零歧义。反之，如果规格没写清，AI 很容易按 COLMAP 的 c2w 惯例写反坐标——**不报错、不崩溃、结果还「看起来合理」，是最危险的静默失败**。

## 经验三：换多模态模型，让 AI 直接「看图」debug

**核心观点**：三维重建的 debug 大量依赖渲染图与点云的可视化检查，靠人肉眼在几百张图里找对齐偏差，既耗时又不可复现。换成能直接读图的模型后，把 debug 图贴给 AI，让它自己看、自己归纳偏差，效率是质变。

**案例**：

- **可检视图前置**：流水线的每一步都产出独立可检查的图——02 步出置信度过滤后的彩色点云（scene.ply）、04 步出重建渲染 vs GT 的对比图。这些图本来就是给人看的，现在直接变成给 AI 看的。
- **工作闭环**：贴图 → AI 指出偏差出现在哪些帧、往哪个方向偏 → 回到代码 file:line 定位根因 → 修复后再贴图确认。例如人脸 finetune 的消融实验（A1–A4）和近景注入实验（06e/06g），一次让 AI 读多组对比图归纳差异，比人逐张翻快一个量级。
- **前后对比**：早期用 glm5.3 只能贴日志 + 文字描述现象，AI 隔着一层转述猜问题；换 deepseek v4.1 后直接读图，「描述偏差」这一步从人的活儿变成 AI 的活儿，人只做判断和决策。
- **注意点**：看图也要有数值判据兜底，不能停在「看起来对齐了」。例如视线交汇求目标点的最小二乘，用正规矩阵条件数判断解是否可信（cond 1.9–2.8 才算良态）——残差小但条件数大，说明解在某个方向上没约束，图再好看也不能信。

## 经验四：保密约束下的本机复现 —— 承认差距，收缩战线

**核心观点**：公司保密制度下，服务器上的代码和数据拿不到，本机用 AI 复现注定达不到与服务器一致的效果与速度——环境不同、数据不同、内部工具链缺失。务实的策略是：**不追求全链路等价，把本机收缩成「方案验证台」，专注特定功能模块**。

**案例**：

- **环境差距**：服务器流水线是 COLMAP → 3DGS → HYPIR → SAM3 全家桶；本机只有 WSL2 + RTX 3090 24G + 56GB 内存。本机从 `doll` env 克隆建出 `vggt_human` env，只承担「前馈重建 + 3DGS 训练」这一段的可行性验证。
- **网络是活的**：GitHub、HuggingFace、各镜像站的可达性两周内就会反转（实测 hf-mirror 镜像挂掉、ghfast 加速证书失效、GitHub 直连反而恢复）。教训：每次动手下载前先 curl 复测，不信上周的结论。
- **gated 模型的坑**：VGGT-Omega 权重在 HF 的 gated 仓库，需要申请访问 + HF_TOKEN，蓝区下载链路单独脚本化（`01_download_models.sh`），一次配好处处复用。
- **补偿手段——口径对齐**：服务器侧工具的算法原理（视线交汇最小二乘、±180° 方位角循环补偿等）与本地实现互相印证，本机跑通的模块可以反过来作为服务器方案评审的论据。「本机 ≠ 服务器」不等于「本机没用」，定位成方案论证与功能验证的平台。
- **心态**：接受差距，把目标定为「特定功能跑通 + 产出方案论证材料」，而不是「整条流水线与服务器对齐」。

## 经验五：同事用得少，应该怎么介绍

给没怎么用过 AI 的同事讲，不要讲「AI 有多强」，要讲「我踩过什么坑、省下了什么时间」。建议按上手成本从低到高分层介绍：

| 层次 | 做什么 | 门槛 |
|---|---|---|
| 1. 问根因 | 粘贴完整日志，要「根因分析 + 具体 file:line」，而不是问「这个报错怎么办」 | 零门槛，当天见效 |
| 2. 文档型任务 | 让 AI 整理实验记录、写 README 初稿、把踩坑写成排错手册（我们的 NOTES.md 里 70% 的条目来自真实报错） | 低 |
| 3. 规范型任务 | 把团队约定写成 AGENTS.md 这类「给 AI 看的规范」，AI 就能跨会话复刻风格——这是「一个人 + AI 稳定产出」的关键 | 中 |
| 4. 方案三段式 | 讨论方案 → 技术文档 → 代码；debug 时贴图让 AI 读 | 中 |
| 5. 诚实性底线 | 不确定的结论让 AI 标【存疑】，数字必须能回原文核对——读起来很顺但没依据的结论，比没有结论更危险 | 意识层面 |

**一个反直觉的总结**：用 AI 的第一生产力不是省下的写代码时间，而是**每一次排错都被迫沉淀成文档**。团队里文档厚的地方，AI 越好用；这就是「越用越值钱」的复利。
